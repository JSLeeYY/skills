这个 skill 确保所有代码修改都经过系统化的影响分析，防止意外破坏现有功能。在进行任何代码变更前，必须先执行完整的安全检查流程。

## 使用场景

在以下情况下必须使用此 skill：
- 修改现有代码（函数、类、组件、样式等）
- 新增可能影响现有代码的功能
- 优化或重构代码
- 复用现有代码到新位置
- 删除或移动代码

## 核心原则

1. **先分析，后修改**：永远不要在不了解影响范围的情况下修改代码
2. **复用需谨慎**：复用代码时必须确保不会影响原有使用场景
3. **全局视角**：考虑修改对整个项目的影响，不仅仅是当前文件
4. **验证优先**：在确认安全之前，不要进行修改

## 安全检查流程

### 第一步：识别修改目标

明确要修改的代码元素：
- 文件路径和具体位置
- 函数名、类名、组件名
- CSS 类名、ID、样式规则
- 变量名、常量名
- API 端点、配置项

**输出**：清晰列出所有要修改的代码元素

### 第二步：搜索所有引用

使用 Grep 工具搜索代码元素在项目中的所有出现位置：

```
对于函数/类/组件：
- 搜索函数名/类名的所有引用
- 搜索 import/require 语句
- 搜索继承或实现关系

对于样式：
- 搜索 CSS 类名在所有 HTML/JSX/模板中的使用
- 搜索样式文件中的引用和继承
- 搜索 JavaScript 中动态添加的类名

对于变量/配置：
- 搜索变量名的所有读取和写入
- 搜索配置项的所有引用
```

**输出**：完整的引用列表，包括文件路径和行号

### 第三步：分析影响范围

对每个引用位置进行分析：

1. **直接影响**：
   - 这个位置如何使用该代码？
   - 修改会改变这里的行为吗？
   - 是否会导致错误或异常？

2. **间接影响**：
   - 依赖这个位置的其他代码有哪些？
   - 是否会影响数据流或控制流？
   - 是否会影响 UI 渲染或样式？

3. **边界情况**：
   - 是否有特殊的输入或状态？
   - 是否有错误处理逻辑依赖当前行为？
   - 是否有测试用例覆盖？

**输出**：影响分析报告，标注高风险、中风险、低风险区域

### 第四步：复用安全性检查

如果是复用现有代码，额外检查：

1. **原始用途分析**：
   - 这段代码在原位置的具体用途是什么？
   - 是否有特定的上下文依赖？
   - 是否有隐含的假设或约束？

2. **新用途适配性**：
   - 新位置的需求与原位置是否完全一致？
   - 是否需要修改参数或配置？
   - 是否会引入新的依赖？

3. **隔离性验证**：
   - 复用后是否会影响原位置的功能？
   - 是否共享状态或副作用？
   - 修改复用代码时是否会影响两处？

**输出**：复用安全性评估，明确指出潜在风险

### 第五步：制定安全修改方案

基于分析结果，制定修改方案：

1. **低风险修改**：
   - 影响范围明确且可控
   - 所有引用都已分析
   - 可以直接修改

2. **中风险修改**：
   - 需要同步修改多个位置
   - 需要更新相关文档或注释
   - 建议增加测试覆盖

3. **高风险修改**：
   - 影响范围广泛或不确定
   - 建议拆分为多个小步骤
   - 每步修改后验证功能
   - 考虑使用特性开关或渐进式迁移

**输出**：详细的修改计划，包括步骤、验证方法、回滚方案

### 第六步：执行修改并验证

按照修改方案执行：

1. **执行修改**：
   - 按计划逐步修改代码
   - 保持每次修改的原子性
   - 及时提交版本控制

2. **功能验证**：
   - 验证修改位置的功能正常
   - 验证所有引用位置的功能正常
   - 运行相关测试用例
   - 检查样式和 UI 是否正常

3. **回归测试**：
   - 测试可能受影响的功能模块
   - 检查边界情况和异常处理
   - 确认没有引入新的 bug

**输出**：验证报告，确认所有功能正常

## 工具使用指南

### 使用 Grep 搜索引用

```
# 搜索函数名
Grep: pattern="functionName", output_mode="content", -n=true

# 搜索 CSS 类名
Grep: pattern="className", glob="**/*.{html,jsx,tsx,vue}", output_mode="content"

# 搜索导入语句
Grep: pattern="import.*from.*'./module'", output_mode="content"
```

### 使用 Read 查看上下文

```
# 读取完整文件了解上下文
Read: file_path="path/to/file.js"

# 读取特定行范围
Read: file_path="path/to/file.js", offset=100, limit=50
```

### 使用 Glob 查找相关文件

```
# 查找所有组件文件
Glob: pattern="**/*Component.tsx"

# 查找所有样式文件
Glob: pattern="**/*.{css,scss,less}"
```

## 常见风险场景

### 1. 修改共享组件

**风险**：影响所有使用该组件的页面

**检查要点**：
- 搜索组件的所有导入位置
- 检查每个使用场景的 props 传递
- 验证样式变更不会破坏布局

### 2. 修改工具函数

**风险**：影响所有调用该函数的代码

**检查要点**：
- 搜索函数的所有调用位置
- 检查参数类型和返回值的兼容性
- 验证边界情况和错误处理

### 3. 修改全局样式

**风险**：影响整个应用的视觉呈现

**检查要点**：
- 搜索 CSS 类名在所有模板中的使用
- 检查样式继承和层叠关系
- 验证响应式布局不受影响

### 4. 复用业务逻辑

**风险**：引入不适用的业务规则或副作用

**检查要点**：
- 分析原业务逻辑的上下文依赖
- 检查状态管理和数据流
- 验证新场景下的业务规则正确性

### 5. 修改 API 接口

**风险**：破坏前后端契约

**检查要点**：
- 搜索 API 端点的所有调用位置
- 检查请求参数和响应格式的兼容性
- 验证错误处理和异常情况

## 最佳实践

1. **不要跳过检查**：即使是"简单"的修改也要执行完整流程
2. **保持怀疑态度**：假设每个修改都可能有隐藏的影响
3. **记录决策**：在代码注释中说明为什么这样修改是安全的
4. **增量修改**：大的修改拆分为多个小步骤，每步都验证
5. **及时沟通**：发现高风险修改时，与团队讨论方案

## 注意事项

- 这个 skill 是强制性的，不是可选的
- 不要因为时间紧迫而跳过安全检查
- 发现问题时，优先修复而不是绕过
- 保持检查报告的完整性，便于后续审查
- 对于不确定的情况，选择更保守的方案

---

**记住**：代码安全检查不是负担，而是保护。花在分析上的时间，远少于修复 bug 的时间。
