# 数据包导出详细操作教程

## 一、文档目的

本文档用于指导非开发人员在具备服务器登录权限的前提下，使用现有导出脚本完成 PECMS 数据包导出、加密打包、解密查看和结果自检。

本文档重点解决四个问题：

1. 现在到底有哪两份脚本，它们分别负责什么。
2. 这两份脚本当前真实部署在什么位置，应该输入什么命令。
3. 每一步操作到底是什么意思，为什么要这样做。
4. 如果脚本报错，应该先从哪里排查。

---

## 二、当前版本核实结论

本教程已根据你在 2026-05-08 提供的两台服务器截图，以及当前更新后的两份脚本副本重新核对，现阶段以以下事实为准。

### 2.1 服务器里的真实脚本位置

| 服务器 | 实际目录 | 实际脚本文件 | 实际用途 |
| --- | --- | --- | --- |
| `ecs-93244365` | `/opt/export` | `huayi-export-v3.sh` | 对外平台按项目导出、解密 |
| `ecs-53680674` | `/opt/export` | `pecms-export.sh` | 对内平台按项目导出、按合同导出、解密 |

因为资料目录里的脚本备份名称，和服务器上的实际执行路径不是一回事。

你当前本地资料目录里看到的是：

1. `export-sh-huayi/huayi-export.sh`
2. `export-sh-huayi/huayi-export-v3.sh`
3. `export-sh-pecms/pecms-export.sh`

这是为了归档和区分脚本来源，便于整理文档。

但真正执行命令时，必须以服务器实际情况为准。当前两台服务器上都已经明确显示：

1. 实际目录都是 `/opt/export`
2. 当前建议执行的是 `huayi-export-v3.sh`
3. 第二台服务器执行的是 `pecms-export.sh`

因此，后续所有命令都必须按照这个真实结果执行，不能再沿用旧目录或旧脚本名。

## 三、两份脚本分别负责什么

### 3.1 `huayi-export-v3.sh`

该脚本用于对外平台数据导出，当前支持两类动作：

1. `export`：按项目 ID 导出数据并加密打包
2. `decrypt`：解密已经生成的 `.tar.gz.enc` 数据包

它不支持按合同号导出。

### 3.2 `pecms-export.sh`

该脚本用于对内平台数据导出，当前支持三类动作：

1. `export`：按项目 ID 导出
2. `export_contract`：按合同号导出
3. `decrypt`：解密已经生成的 `.tar.gz.enc` 数据包

### 3.3 这两份脚本共同完成的事情

不论是对外脚本还是对内脚本，最终做的事情本质上都一样：

1. 先验证你传入的项目 ID 或合同号是否存在
2. 导出数据库中的相关业务数据，保存为多个 `.sql` 文件
3. 归集这些业务数据关联的附件 ID
4. 从服务器附件目录中复制真实附件文件
5. 生成临时导出目录
6. 打包压缩
7. 再加密成一个最终交付文件 `.tar.gz.enc`

也就是说，它导出的不是单条记录，而是一整套“业务数据 + 附件文件”的交付包。

## 四、当前脚本内部工作方式说明

这部分不是让你改脚本，而是帮助你理解：为什么有些错误需要查服务器环境，而不是只看命令本身。

### 4.1 `pecms-export.sh` 以 `/root/.my.cnf` 为来源，但不是直接原样使用

优化后的 `pecms-export.sh` 仍然把 `/root/.my.cnf` 作为数据库连接信息来源，但它在真正执行 `mysql` 和 `mysqldump` 前，会先做两件事：

1. 读取 `/root/.my.cnf` 中的 `[client]` 段
2. 生成一个临时客户端配置文件，并剔除 `database`、`thread_handling` 这类不适合直接原样传给客户端的配置项

随后脚本实际调用更接近下面这种方式：

```bash
mysql --defaults-file=<脚本临时生成的配置> <数据库名>
mysqldump --defaults-file=<脚本临时生成的配置> <数据库名> <表名>
```

其中数据库名的取值优先级是：

1. 优先使用当前 shell 环境里的 `MYSQL_DATABASE`
2. 如果没有设置，再读取 `/root/.my.cnf` 里的 `database=...`

这表示：

1. 脚本真正连接哪一套数据库，仍然要以服务器环境为准，不是看你自己电脑上的数据库客户端连了哪里
2. 如果 `/root/.my.cnf` 里没有 `database=`，但执行前临时设置了 `MYSQL_DATABASE`，脚本仍可能正常运行
3. 你手工执行 `mysql --defaults-extra-file=/root/.my.cnf ...` 如果报错，不一定等于脚本也会报同样错误，因为脚本内部先做了配置清洗

### 4.2 对外平台 `huayi-export-v3.sh` 不再把大批量 ID 拼成超长字符串

当前对外平台优化版 `huayi-export-v3.sh` 不依赖早期那种把大量 ID 先 `GROUP_CONCAT` 成超长字符串、再拼进 `IN (...)` 的做法，而是把“项目 -> 派遣单 -> 文档”的关系保留为子查询 SQL，直接交给数据库执行。

你可以把这个过程理解为：

1. 先按项目 ID 找到对应的派遣单
2. 再按派遣单找到对应文档
3. 再沿着这些关系继续导出日志、报表、表单、附件等相关数据

这样做的直接意义是：

1. 避免大项目时因为 ID 列表过长而被截断
2. 避免再次出现 `Argument list too long`
3. 让导出链条在大项目场景下更稳定

### 4.3 `pecms-export.sh` 会区分“空表”和“导出失败”，但失败不会整包中止

当前优化后的 `pecms-export.sh` 处理方式是：

1. 先用 `mysqldump` 导出某张表
2. 导出的 `.sql` 采用带字段名的 `INSERT INTO 表名 (字段1, 字段2, ...) VALUES ...` 形式
3. 如果导出结果里根本没有 `INSERT INTO`，脚本会把这张表记为 `empty`，删除空 `.sql`
4. 如果 `mysqldump` 本身失败，脚本会删除该表的 `.sql` 和 `.err`，把状态记为 `failed`，然后继续后面的表

这一步非常关键，它意味着：

1. 生成了最终 `.tar.gz.enc`，并不自动等于“所有表都导出成功”
2. 你看到“某张表的 `.sql` 文件不存在”，有两种可能：该表确实无数据，或者该表导出失败
3. 判断是否完整，必须解密后查看 `export_time.tsv`，不能只看有没有生成包

### 4.4 `pecms-export.sh` 会先生成附件清单，再优先用 `rsync` 批量复制

脚本在导出业务表后，会继续导出：

1. `sys_file_upload`
2. `sys_file`
3. `attachment_files.txt` 附件路径清单

随后它会按数据库中的 `file_path` 去服务器磁盘上复制真实附件文件，统一放到导出目录下的：

```text
attatchments
```

复制附件时的规则是：

1. 如果服务器安装了 `rsync`，优先走批量复制
2. 如果没有 `rsync`，再回退到逐个文件 `cp`
3. 找不到的附件会打印 `Missing file: ...`，但不会因此中止整次导出

### 4.5 `pecms-export.sh` 会额外生成核对文件，再压缩加密

脚本正常跑完导出阶段后，临时目录里通常不只有 `.sql` 文件和 `attatchments`，还会出现：

1. `export_time.tsv`：逐表记录 `ok / empty / failed`、耗时和字节数
2. `attachment_files.txt`：本次准备复制的附件相对路径清单（有附件时通常会保留）

随后脚本会：

1. 如果服务器安装了 `pigz`，优先使用 `tar -I pigz` 加速压缩
2. 如果没有 `pigz`，退回普通 `tar czf`
3. 再用 `openssl enc -aes-256-cbc` 生成最终 `.tar.gz.enc`
4. 只有压缩加密成功，才删除原始导出目录

因此，通常最终交付件仍是当前目录下的一个 `.tar.gz.enc` 文件，但判定“导出是否完整”时，必须把解密后的 `export_time.tsv` 也一起纳入检查。

## 五、正式操作前必须理解的几个概念

### 5.1 什么是项目 ID

项目 ID 不是项目名称，也不是项目编号。

它对应的是数据库中的主键字段，当前脚本校验项目时查的是：

```text
project_management.id
```

如果这里传错，脚本会直接报：

```text
ERROR: project id not found: <PROJECT_ID>
```

### 5.2 什么是合同号

合同号是业务上的合同编号，不是项目 ID。

当前 `pecms-export.sh` 按合同导出时，先校验的是：

```text
supervision_department_contract.code
```

同时它会再从派遣单表中按照合同号去找关联派遣单：

```text
project_dispatch.supervisor_contract_no
```

因此，合同号模式是“按合同维度”打包，不是“按项目主键”打包。

如果合同号本身查不到，脚本当前会直接报：

```text
ERROR: contract not found: <CONTRACT_NO>
```

### 5.3 什么是 `FILE_ROOT`

`FILE_ROOT` 是附件根目录。

当前脚本配置为：

```text
/opt/apphome/iipFile/attach
```

它的含义是：

1. 数据库里记录的是附件的业务路径
2. 脚本会把该路径拼接到 `FILE_ROOT` 后面
3. 再去服务器磁盘上查找真实文件并复制

如果这个目录不对，或者当前用户没有读取权限，就会出现附件复制失败或“文件不存在”提示。

### 5.4 什么是 `/root/.my.cnf`

这是 MySQL 客户端使用的配置文件，不是导出目录，也不是导出结果。

它通常保存了数据库连接所需的参数，例如：

1. 数据库地址
2. 端口
3. 用户名
4. 密码
5. 默认字符集

对于当前优化后的 `pecms-export.sh`，它的作用有两层：

1. 提供 `host / port / user / password` 等客户端连接参数
2. 在未显式设置 `MYSQL_DATABASE` 时，提供默认库名 `database=...`

因此你必须理解一点：

1. 脚本连哪套数据库，首先看服务器上的 `/root/.my.cnf`
2. 如果执行前临时设置了 `MYSQL_DATABASE`，最终库名会优先以该环境变量为准
3. 人工排查时，不要只凭本地 Navicat 截图判断环境是否一致

### 5.5 什么是 `ENCRYPT_PASSWORD`

这是脚本用于加密压缩包的密码。

它用于两个阶段：

1. 导出后加密打包
2. 后续解密查看

因此，如果密码被修改，旧包和新包未必能互相解开。出于安全原因，本文档不重复抄写密码明文，实际操作以服务器脚本当前配置为准。

### 5.6 什么是 `.sql` 文件

导出结果中的 `.sql` 文件，不是给业务人员直接双击看的普通文档，而是数据库记录的文本化结果。

在当前优化后的 `pecms-export.sh` 中，`.sql` 默认由 `mysqldump --complete-insert` 生成，所以常见形式是带字段名的：

```text
INSERT INTO 表名 (字段1, 字段2, ...) VALUES ...
```

它的主要用途是：

1. 提供给开发或数据库人员导入
2. 做数据留档
3. 做交付核对
4. 做问题追溯

## 六、运行环境要求

### 6.1 必须在 Linux 服务器上执行

这套脚本不能在当前 Windows 文件夹里直接双击运行，必须登录目标 Linux 服务器后执行。

原因很简单，脚本依赖：

1. `bash`
2. `mysql`
3. `mysqldump`
4. `tar`
5. `openssl`
6. `/root/.my.cnf`
7. 服务器上的附件目录

另外，`pecms-export.sh` 还会根据服务器环境决定是否启用：

1. `rsync`：用于更快复制附件
2. `pigz`：用于更快压缩打包

这些条件一般只在正式服务器或专门的数据导出服务器上具备。

### 6.2 建议提前检查的命令

进入服务器后，建议先执行：

```bash
mysql --version
mysqldump --version
tar --version
openssl version
```

如果这些命令都能正常返回版本信息，说明基础运行环境大体可用。

如果想进一步确认 PECMS 优化版是否能跑得更快，也可以额外检查：

```bash
rsync --version
pigz --version
```

这两个不是必须条件；没有它们时，脚本只是会退回较慢的兼容分支。

### 6.3 需要具备的权限

执行人员至少需要具备以下权限：

1. 可以登录对应 Linux 服务器
2. 可以进入 `/opt/export`
3. 可以执行对应脚本
4. 可以读取 `/root/.my.cnf`
5. 可以读取 `/opt/apphome/iipFile/attach`
6. 当前目录有足够空间生成临时目录和加密包

### 6.4 关于磁盘空间

导出过程中会先生成临时目录，再打包加密。因此在导出未结束前，磁盘上会同时存在：

1. 多个 `.sql` 文件
2. 附件复制结果
3. 压缩包
4. 加密包

如果项目附件很多，磁盘空间不足会直接导致中途失败。建议预留数 GB 以上可用空间。

## 七、正式操作前的标准检查步骤

下面这部分建议严格按顺序执行，尤其适合第一次操作的人。

### 第 1 步：先判断导出类型

先确认你要导出的是什么：

1. 对外平台项目数据
2. 对内平台项目数据
3. 对内平台合同数据

对应关系如下：

| 需求类型 | 登录服务器 | 使用脚本 | 参数类型 |
| --- | --- | --- | --- |
| 对外平台按项目导出 | `ecs-93244365` | `huayi-export-v3.sh` | `PROJECT_ID` |
| 对内平台按项目导出 | `ecs-53680674` | `pecms-export.sh` | `PROJECT_ID` |
| 对内平台按合同导出 | `ecs-53680674` | `pecms-export.sh` | `CONTRACT_NO` |

### 第 2 步：登录目标服务器

示例：

```bash
ssh 用户名@服务器IP
```

如果你已经在服务器终端中，这一步可以跳过。

### 第 3 步：进入脚本目录

当前两台服务器真实脚本目录都是：

```bash
cd /opt/export
```

这一步的作用是：确保你后续执行的 `./脚本名` 指向当前服务器上的真实脚本文件。

### 第 4 步：确认脚本文件存在

对外平台执行：

```bash
ls -l huayi-export-v3.sh
```

对内平台执行：

```bash
ls -l pecms-export.sh
```

如果能看到文件信息，说明脚本文件确实在当前目录中。

### 第 5 步：赋予执行权限

对外平台：

```bash
chmod +x huayi-export-v3.sh
```

对内平台：

```bash
chmod +x pecms-export.sh
```

这一步的含义是：给脚本添加“可执行”权限。如果跳过，后面可能报：

```text
Permission denied
```

### 第 6 步：检查脚本关键配置

对外平台：

```bash
head -40 huayi-export-v3.sh
```

对内平台：

```bash
grep -nE 'FILE_ROOT|MYSQL_CNF|MYSQL_DATABASE|complete-insert|export_time.tsv|attachment_files.txt|rsync|pigz' pecms-export.sh
```

对外平台优化版重点核对四件事：

1. 是否存在 `FILE_ROOT`
2. 是否存在 `ENCRYPT_PASSWORD`
3. 是否统一使用 `/root/.my.cnf`
4. 是否存在 `--complete-insert`

当前最新对外平台脚本中，这四项都应明确存在。

对内平台优化版至少应能看到以下关键信息：

1. `FILE_ROOT`
2. `MYSQL_CNF`
3. `MYSQL_DATABASE`
4. `--complete-insert`
5. `export_time.tsv`
6. `attachment_files.txt`
7. `rsync` 与 `pigz` 的分支逻辑

### 第 7 步：确认 `/root/.my.cnf` 指向的数据库环境

这是非常关键的一步，尤其适合排查“数据库里明明有，但脚本说没有”的情况。

可以先查看非敏感配置项和当前环境变量：

```bash
grep -E '^(host|port|user|database)=' /root/.my.cnf
echo "$MYSQL_DATABASE"
```

这一步的作用是：

1. 确认脚本实际连接的是哪台数据库
2. 确认端口、文件中的默认库名，以及当前 shell 是否额外设置了 `MYSQL_DATABASE`
3. 避免你在本地客户端查的是 A 库，脚本实际查的是 B 库
4. 如果文件里没有 `database=`，且 `MYSQL_DATABASE` 也是空的，脚本会直接报 `ERROR: no database configured; set database=... in /root/.my.cnf or MYSQL_DATABASE=...`

### 第 8 步：确认附件根目录存在

```bash
ls -ld /opt/apphome/iipFile/attach
```

如果该目录不存在，或者当前用户没有读取权限，后续即使导出出 `.sql`，附件也可能复制失败。

## 八、对外平台按项目 ID 导出

本节适用于：

1. 你要导出的是对外平台数据
2. 你手上拿到的是项目 ID
3. 你登录的是 `ecs-93244365`
4. 你使用的是 `/opt/export/huayi-export-v3.sh`

如果你在服务器的 `/opt/export` 目录里暂时还看不到 `huayi-export-v3.sh`，说明当前服务器还没有替换到优化版脚本。此时应先将 `huayi-export-v3.sh` 部署到该目录，再按本节命令执行。

### 8.1 标准命令

```bash
cd /opt/export
chmod +x huayi-export-v3.sh
./huayi-export-v3.sh export <PROJECT_ID> 
```

示例：

```bash
./huayi-export-v3.sh export 7637bdc0191a4d51a16f64d950ecb8d0
```

### 8.2 这条命令每一段是什么意思

1. `./huayi-export-v3.sh`：执行当前目录里的对外平台优化版脚本
2. `export`：告诉脚本，这次要做的是“导出并打包”
3. `<PROJECT_ID>`：要导出的项目主键 ID

### 8.3 建议先做一次存在性核对

如果要在正式导出前先查“项目是否存在”，建议由具备数据库操作能力的技术人员在同一台服务器上核对，不要只凭本地数据库客户端截图判断。

实际核对时，至少应先确认三件事：

1. 当前服务器实际使用的是哪套数据库环境
2. 传入的值确实是 `project_management.id`
3. 本地客户端与服务器侧看到的是不是同一套环境

### 8.4 脚本内部会按什么顺序处理

对外平台 `huayi-export-v3.sh` 当前的大体处理顺序如下：

1. 在 `project_management` 中校验项目是否存在
2. 取出项目名称
3. 生成“项目名称 + 时间戳”的临时导出目录
4. 把该项目对应的派遣单关系保留为子查询
5. 再把文档关系保留为子查询
6. 按各业务表依次用 `mysqldump` 导出为带字段名的 `.sql`
7. 归集附件业务 ID
8. 导出附件相关表
9. 从 `FILE_ROOT` 指向的服务器目录批量复制真实附件
10. 打包压缩并加密
11. 删除临时目录

## 十二、遇到“数据库里明明有，脚本却说不存在”时怎么排查

这是最容易让人误判的一类问题。

### 12.1 先理解根本原因

如果你在自己电脑上的数据库工具里能查到数据，但脚本报：

```text
ERROR: project id not found: <PROJECT_ID>
```

最常见的原因不是脚本坏了，而是：

1. 你本地数据库工具连的是一套库
2. 服务器上的 `/root/.my.cnf` 指向的是另一套库
3. 当前 shell 里的 `MYSQL_DATABASE` 又可能把最终库名切到了另一套库
4. 两边库名可能一样，但数据库实例不是同一个

### 12.2 正确排查顺序

第一步，在服务器上查看脚本实际使用的数据库环境：

```bash
grep -E '^(host|port|user|database)=' /root/.my.cnf
echo "$MYSQL_DATABASE"
```

第二步，确认你传入的值是否真的是 `project_management.id`，而不是项目编号、项目名称、派遣单 ID 或合同号。

第三步，如需进一步查库，建议由技术人员按脚本同样的服务器环境和客户端配置方式排查，不要简单把原始 `/root/.my.cnf` 直接套进旧命令就下结论。

第四步，如果服务器侧排查不到，而你本地客户端查得到，就说明两边查的不是同一套数据库，或者最终库名来源不一致。

### 12.3 对合同号同样适用

如果是按合同导出报：

```text
ERROR: contract not found: <CONTRACT_NO>
```

排查思路完全相同，只是最终核对的字段换成 `supervision_department_contract.code`。

### 12.4 这一条为什么必须写进教程

因为从当前脚本结构看，数据库连接信息虽然仍然来源于 `/root/.my.cnf`，但最终库名还可能受 `MYSQL_DATABASE` 影响。今后遇到“明明库里有”的争议，必须先统一到“脚本实际连的库”这个标准上，不能只凭本地截图判断。

## 十三、常见问题与处理建议

### 13.1 提示 `Permission denied`

含义：脚本没有执行权限。

处理：

```bash
chmod +x huayi-export-v3.sh
chmod +x pecms-export.sh
```

根据当前场景执行其中一条即可。

### 13.2 提示 `mysql: command not found` 或 `mysqldump: command not found`

含义：服务器没有安装 MySQL 客户端工具，或者命令未加入 PATH。

处理：

```bash
mysql --version
mysqldump --version
```

如果命令不存在，请联系运维或管理员处理环境。

### 13.3 提示 `Access denied for user`

含义：数据库账号、密码或数据库授权有问题。

处理思路：

1. 检查 `/root/.my.cnf` 是否存在
2. 检查当前用户是否有权限读取该文件
3. 联系数据库管理员确认账号授权

### 13.4 提示项目不存在或合同不存在

处理顺序建议如下：

1. 先核对输入值有没有输错
2. 再确认 `/root/.my.cnf` 和 `MYSQL_DATABASE` 的组合到底指向哪套库
3. 再确认本地数据库工具和服务器是否连接的是同一环境

### 13.5 提示附件复制失败或大量 `文件不存在`

常见原因：

1. `FILE_ROOT` 路径不对
2. 服务器上对应附件已被物理删除
3. 当前执行用户没有读取附件目录权限
4. 数据库中的附件路径与磁盘实际路径不一致

处理建议：

1. 检查脚本头部的 `FILE_ROOT`
2. 检查 `/opt/apphome/iipFile/attach` 是否存在
3. 抽查日志中报出的具体文件路径
4. 解密后同时检查 `attachment_files.txt`
5. 必要时联系开发或运维核对附件存储策略

### 13.6 提示 `bad decrypt`

含义通常有两种：

1. 当前脚本中的加密密码和导出时使用的密码不一致
2. 数据包文件已经损坏

处理建议：

1. 核对当前脚本配置
2. 检查文件传输是否完整
3. 如仍失败，重新导出一份

### 13.7 生成的包特别小

如果最终 `.tar.gz.enc` 只有很小的体积，而你预期应该包含大量附件，通常需要重点怀疑：

1. 项目本身数据很少
2. 附件没有复制成功
3. 传入的项目 ID 或合同号不对
4. 导出的环境不是你想要的那套库
5. 某些关键表在 PECMS 导出过程中被记成了 `failed`

### 13.8 终端出现 `Export failed, skipped`

这说明某一张表的 `mysqldump` 已经失败，但 `pecms-export.sh` 选择记录失败并继续后续导出。

这时不要只因为最终生成了 `.tar.gz.enc` 就判定成功，正确做法是：

1. 记下失败发生前后的表名
2. 解密结果包，查看 `export_time.tsv` 中哪些表被记成了 `failed`
3. 让技术人员根据失败表继续排查 SQL 条件、权限、库结构或客户端环境

## 十四、导出完成后的自检方法

建议至少做以下检查。

### 14.1 检查是否真的生成了加密包

```bash
ls -lh *.tar.gz.enc
```

### 14.2 检查结果文件大小是否明显异常

如果你预期应包含大量附件，而最终文件却只有几十 KB 或几百 KB，就应进一步排查。

### 14.3 至少解密抽查一次

建议至少解密一份结果，确认里面确实存在：

1. 多个 `.sql` 文件
2. `attatchments` 附件目录
3. `export_time.tsv`
4. 如有附件，还应重点看 `attachment_files.txt`

### 14.4 必查 `export_time.tsv` 中是否存在 `failed`

如果 `export_time.tsv` 中出现 `failed`，说明某些表并没有成功导出。即使最终加密包已经生成，这次导出也不能直接当作完整交付件使用。

### 14.5 注意空 `.sql` 文件被自动删除这一事实

如果某些业务表对应的 `.sql` 文件没有出现，不要马上认定脚本遗漏。当前版本脚本会自动删除空文件，因此也可能是该表本身没有数据。

## 十六、最后提醒

这套脚本本质上不是一个“普通办公文件”，而是一套依赖服务器环境、数据库配置和附件存储目录的数据导出工具。

1. 你传入的项目 ID 或合同号是否正确

3. 附件根目录 `/opt/apphome/iipFile/attach` 是否可访问
4. 解密后的 `export_time.tsv` 是否没有出现 `failed`

只有这四点同时成立，才能把这次导出视为真正完成。
