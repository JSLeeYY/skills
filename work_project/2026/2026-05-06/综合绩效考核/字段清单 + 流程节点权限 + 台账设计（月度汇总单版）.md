# 字段清单 + 流程节点权限 + 台账设计（月度汇总单版）

## 1. 设计范围

本文基于 `南京三方部门月度绩效考核标准.xlsx`，按“月度集中填报”的实际业务口径，输出综合管理平台的落地设计，包含：

- 规则库字段设计
- 月度绩效汇总打分单字段设计
- 流程节点权限设计
- 事件台账与月度汇总台账设计

本文采用的业务模型为：

**规则库 + 月度汇总打分单（主表+子表）+ 事件台账 + 月度汇总台账**

即：

- 每月每个提报部门发起 1 张或多张月度汇总单
- 每张汇总单主表记录本批次公共信息
- 子表每一行代表 1 条具体加分/扣分事件
- 审批通过后，子表逐行写入绩效事件台账
- 月度结果再由事件台账自动汇总

## 2. 对象总览

建议在平台中建设以下 4 类核心对象：

| 对象名称 | 类型 | 作用 |
| --- | --- | --- |
| 绩效规则库 | 数据建模主表 | 维护所有加分/扣分标准 |
| 月度绩效汇总打分单 | 流程表单（主表+子表） | 每月集中填报一批打分事件 |
| 绩效事件台账 | 数据建模台账 | 保存审批通过后的每一条子表事件 |
| 月度绩效汇总台账 | 数据建模台账/报表 | 汇总每人每月加扣分结果 |

另建议保留：

- 审批日志查询视图
- 员工个人绩效查询视图
- 月度批次查询视图

## 3. 业务模型说明

### 3.1 为什么改成月度汇总单

如果实际业务不是“发生一条提一条”，而是“月底集中统计后一并提交”，则采用一事一单会带来：

- 发起单据数量过多
- 批量录入成本高
- 月底集中整理时重复操作多

因此本版改为：

- 主表存一整批公共信息
- 子表逐行录入具体事件

### 3.2 本版方案的关键取舍

本方案提高了录入效率，但要接受以下系统特征：

- 流程审批以整单为主，不是逐行独立审批
- 若其中 1 行有问题，通常退回整单修改
- 审批通过后，需把子表逐行拆入事件台账
- 被打分人通知若要做到逐人逐条，需要额外按子表生成消息

因此建议本版先按“整单审批、整单退回、逐行入账”实施。

## 4. 规则库字段清单

规则库用于承接 Excel 的两张 sheet。建议单独建设基础表，不走审批流程。

## 4.2 分值模型建议口径

| 分值模型 | 适用示例 | 系统处理建议 |
| --- | --- | --- |
| 固定值 | `每次扣2分` | 自动带出固定分值 |
| 区间值 | `每次加1-5分` | 人工填写实际分值，系统校验范围 |
| 累乘型 | `每延迟1个工作日扣0.5分` | 录入次数/天数，系统自动乘算 |
| 分档型 | `每次扣15/30分` | 需选择严重程度，再带出具体分值 |
| 公式型 | `每10万1分，上限25分` | 录入基数，系统按公式计算 |

## 5.3 子表联动建议

| 联动编号 | 条件 | 动作 |
| --- | --- | --- |
| `L01` | 选择 `rule_code` | 自动带出规则标题、细分事项、附加事项、分值规则、分值模型 |
| `L02` | `score_model=固定值` | 自动带出 `actual_score`，设为只读 |
| `L03` | `score_model=区间值` | `actual_score` 可编辑，并校验在 `min_score~max_score` 之间 |
| `L04` | `score_model=累乘型` | 显示 `occur_count` 或 `base_quantity` |
| `L05` | `score_model=分档型` | 显示 `severity_level` |
| `L06` | 规则要求附件 | `evidence_attachment` 设为必填 |
| `L07` | 子表变更 | 自动重算主表 `item_count`、`total_add_score`、`total_ded_score`、`total_net_score` |
| `L08` | 审核节点填写 `review_adjust_score` | 行 `score_result` 暂按审核分值预览 |
| `L09` | 审批节点填写 `approve_adjust_score` | 行 `score_result` 以审批分值为准 |

## 5.4 子表使用规则

为降低首版复杂度，建议明确以下规则：

- 一行只允许选择一条规则
- 一行只对应一名被打分人
- 一行只处理一条具体绩效事件
- 一张单允许录入多行
- 同一张单允许同时出现加分和扣分行，但建议按管理习惯决定是否分开提报

如果业务上希望加分和扣分完全分开管理，也可以增加限制：

- 主表增加 `batch_score_type`
- 子表中的 `score_type` 自动继承主表，不允许混填

## 6. 流程节点权限设计

## 6.1 推荐流程节点

1. `月度提报`
2. `归口审核`
3. `最终审批`
4. `结果入账`

## 6.2 节点权限表

| 节点 | 处理人 | 可编辑范围 | 说明 |
| --- | --- | --- | --- |
| 月度提报 | 各部门部长/分管领导 | 主表公共信息；子表业务字段 | 发起人录入本月多条事件 |
| 归口审核 | 赵洵/许开明 | 主表 `review_decision`、`review_opinion`；子表 `review_adjust_score` | 审核本批次是否属实、分值是否合理 |

| 结果入账 | 系统节点 | 无人工编辑 | 子表逐行写台账并通知 |

## 6.6 各节点只读字段

除当前节点允许编辑的字段外，其余字段建议设为只读，尤其是：

- 规则带出字段
- 已审核意见
- 已审批意见
- 系统状态字段
- 已固化的统计字段

## 6.7 节点处理建议

### 月度提报节点

- 主表必须填写考核月份
- 子表每行必须填写被打分人、规则、事实说明
- 如规则要求附件，则该行附件必填
- 如规则是区间值，则该行实际分值必填并校验范围

### 归口审核节点

- 可通过、退回、驳回
- 可调整子表分值，但建议填写审核意见
- 若发现某一行有问题，首版建议整单退回，不做部分通过

### 最终审批节点

- 可同意、退回、驳回
- 如调整任一子表分值，审批意见必填
- 审批通过后写入每一行最终分值

### 结果入账节点

- 自动按子表逐行写绩效事件台账
- 自动更新月度汇总台账
- 自动向对应被打分人发送消息

## 7. 路由与校验规则

## 7.1 路由规则

| 条件 | 流向 |
| --- | --- |
| 发起提交 | 归口审核 |
| 审核通过 | 最终审批 |
| 审核退回 | 返回发起人 |
| 审核驳回 | 流程结束 |
| 审批同意 | 结果入账 |
| 审批退回 | 返回发起人 |
| 审批驳回 | 流程结束 |

## 7.2 主表校验规则

| 编号 | 校验内容 |
| --- | --- |
| `M01` | `assessment_month` 不可为空 |
| `M02` | 子表至少保留 1 行有效事件 |
| `M03` | `item_count` 必须与子表有效行数一致 |

## 7.3 子表校验规则

| 编号 | 校验内容 |
| --- | --- |
| `S01` | `actual_score` 不可为空 |
| `S02` | 固定值规则下，`actual_score` 必须等于固定分值 |
| `S03` | 区间值规则下，`actual_score` 必须在最小值和最大值之间 |
| `S04` | 累乘型规则下，`occur_count` 或 `base_quantity` 必须填写 |
| `S05` | 规则要求附件时，该行附件必传 |
| `S06` | 被打分人不能为空 |
| `S07` | 同一员工、同一月份、同一规则、同一事件日期，如业务不允许重复，应提示校验 |

## 12. 本方案中的关键说明

### 12.1 本方案不是一事一单

本文采用的是：

- 一张单一个月度批次
- 一张单内多条子表事件
- 一条子表行一条规则

### 12.2 首版不建议做逐行独立流转

虽然子表是逐行事件，但首版不建议做：

- 某几行通过、某几行退回
- 同一单内不同行走不同审批结果
- 子表级单独流程状态

原因是：

- 泛微标准流程更适合整单审批
- 逐行流转配置复杂度高
- 后续台账同步和通知拆分也更复杂

### 12.3 如后续需要更精细控制

可以再扩展：

- 子表增加 `row_review_result`
- 子表增加 `row_approve_result`
- 子表增加 `row_reject_reason`
- 子表增加 `row_effective_flag`

但建议在首版上线稳定后再做。
