# 三服务器磁盘治理与共享盘落盘技术实施方案

## 1. 文档说明

- **交付目标**：在不修改业务代码、不修改业务服务日志写入配置、不进行大面积停机的前提下，将三套业务系统的 **MySQL 数据、宿主机业务日志、系统运行日志** 从本地系统盘迁移到 2T 共享云盘上，并保留原始路径不变，实现业务无感知落盘。
- **实施方式**：以 **目录 bind mount 为主、软链接为辅**；按服务器分别交付实施脚本；按业务系统汇报，按节点落地。
- **重要前提**：
  1. 本方案 **不迁移 Docker 容器日志**；
  2. 本方案 **不迁移程序二进制/安装目录**（如 `/opt` 下程序包），仅迁移 MySQL、宿主机业务日志、系统日志；
  3. 实施窗口采用 **单台、单服务、短暂停服切换**，具体时间由现场后续指定；
  4. 日志目录采用 **“自动发现 + 作用说明 + 人工确认 + 批量迁移”** 模式，避免误迁无关目录。

## 3. 总体架构设计

## 3.1 生产可用设计原则

**严禁**三台服务器同时以读写方式直接挂载同一个 ext4 文件系统。  
原因：ext4 不是集群文件系统，多主机同时读写同一 ext4 块设备存在元数据损坏与文件系统损坏风险，**不能作为生产方案**。

因此，本方案采用 **“共享云盘分区独占模型”**：

1. 在共享云盘 `/dev/sdb` 上重新划分三个独立分区；
2. 每个服务器仅挂载属于自己的分区；
3. 每个服务器在本地统一使用 `/filedata/nodeX` 作为共享盘入口；
4. 再通过 bind mount / 软链接，让原始业务路径仍保持不变。

### 3.2 分区规划

> 说明：由于当前整盘 ext4 仅少量占用（Node3 `/filedata` 使用量约 139M），可在实施窗口内卸载后重新分区。重新分区后，原整盘 UUID 将失效，需使用新分区 UUID 重新写入 `/etc/fstab`。

| 分区 | 挂载对象 | 建议容量 | 建议标签 | 挂载点 |
|---|---|---:|---|---|
| `/dev/sdb1` | 192.168.0.111 | 500G | `FILEDATA_NODE1` | `/filedata/node1` |
| `/dev/sdb2` | 192.168.0.3 | 800G | `FILEDATA_NODE2` | `/filedata/node2` |
| `/dev/sdb3` | 192.168.0.4 | 其余全部 | `FILEDATA_NODE3` | `/filedata/node3` |

> 若现场确认 Node1/Node3 MySQL 数据规模明显大于预期，可调整为 `600G / 800G / 其余`，原则不变。

### 3.3 逻辑架构图

```text
/dev/sdb
├─ /dev/sdb1  -> 192.168.0.111 -> /filedata/node1
├─ /dev/sdb2  -> 192.168.0.3   -> /filedata/node2
└─ /dev/sdb3  -> 192.168.0.4   -> /filedata/node3

每台服务器本地统一结构：
/filedata/nodeX/
├─ mysql/
├─ logs/
│  ├─ services/
│  └─ system/
└─ meta/
   ├─ manifests/
   ├─ rollback/
   └─ logs/
```

### 3.4 技术路线

- **MySQL 数据目录**：使用 `bind mount`
- **宿主机业务日志目录**：优先使用 `bind mount`
- **离散单文件日志**：使用软链接
- **系统日志**：先发现并生成人工确认清单，再按清单执行 bind/symlink
- **Docker 容器日志**：不纳入本次迁移

以下目录由各节点初始化脚本自动创建：

```text
/filedata/nodeX/
├─ mysql/
│  ├─ mysql57_3603/
│  ├─ mysql3308/
│  └─ weaver3306/
├─ logs/
│  ├─ services/
│  │  ├─ app_001/
│  │  ├─ nginx/
│  │  └─ ...
│  └─ system/
│     ├─ var_log/
│     ├─ audit/
│     └─ ...
└─ meta/
   ├─ manifests/
   │  ├─ approved_logs.tsv
│   │  ├─ discovered_logs.tsv
│   │  └─ migration_state.tsv
   ├─ rollback/
   └─ logs/
```

### 4.1 目录命名规则

- MySQL 目录：按 **实例名 / 端口 / 版本特征** 命名，禁止使用模糊名
- 服务日志目录：按 **服务名** 命名，如 `nginx`、`portal`、`cas`、`oa`、`security-platform`
- 系统日志目录：按 **原始路径语义** 命名，如 `var_log`、`audit`

### 4.2 权限规范

- 目录默认权限：`0755`
- MySQL 数据目录：按原属主属组恢复（通常 `mysql:mysql`）
- 宿主机服务日志目录：按原目录属主属组恢复
- 回滚元信息目录：`root:root`

## 6. MySQL 迁移实施方案

## 6.1 统一迁移原则

- 不修改业务配置文件中的 datadir 路径
- 保持原始 datadir 路径不变
- 迁移后通过 `mount --bind` 把共享盘目录重新挂回原 datadir
- 切换前必须停库，切换后必须验证启动
- 本地原目录改名保留为 `.bak_YYYYmmddHHMMSS`，用于一键回滚

## 6.2 通用迁移流程

```text
1. 停止 MySQL 实例
2. 校验目标共享目录存在且权限正确
3. rsync 原 datadir -> 共享盘目标目录
4. mv 原 datadir -> datadir.bak_时间戳
5. mkdir 原 datadir
6. mount --bind 共享盘目标目录 -> 原 datadir
7. 写入 /etc/fstab 持久化
8. 启动 MySQL 实例
9. 验证端口、socket、进程、读写
```

## 6.3 各实例映射表

| 业务系统 | 原 datadir | 共享盘目标目录 | 挂回原路径 |
|---|---|---|---|
| 三方、安全平台 | `/data/mysql57/data` | `/filedata/node1/mysql/mysql57_3603` | `/data/mysql57/data` |
| 门户/CAS/泛微 3308 | `/opt/mysql/mydata/3308/data` | `/filedata/node2/mysql/mysql3308` | `/opt/mysql/mydata/3308/data` |
| 门户/CAS/泛微 3306 | `/usr/local/weaver_mysql/data` | `/filedata/node2/mysql/weaver3306` | `/usr/local/weaver_mysql/data` |
| 对外平台 | `/data/mysql57/data` | `/filedata/node3/mysql/mysql57_3603` | `/data/mysql57/data` |

## 6.4 MySQL 验证项

- `ps -ef | grep mysqld`
- `ss -lntp | grep 3306|3308|3603`
- `mysqladmin ping`
- 校验 socket 文件存在
- 抽查建表/查询/写入临时数据
- `mount | grep datadir`
- `df -h` 确认原 datadir 已落到 `/filedata/nodeX/...`

## 7. 日志迁移实施方案

## 7.1 日志发现策略

为避免误迁，本方案不直接迁移所有 `log` 目录，而是先由脚本生成 `discovered_logs.tsv`，至少包含以下字段：

| 字段 | 说明 |
|---|---|
| approved | 是否批准迁移，默认 `N` |
| type | `dir` / `file` |
| path | 原始路径 |
| service | 归属服务 |
| description | 日志用途说明 |
| target_subdir | 共享盘落点子目录 |
| method | `bind` / `symlink` |
|

### 7.1.1 系统日志默认候选说明

| 路径 | 说明 | 建议 |
|---|---|---|
| `/var/log` | 系统日志根目录 | 可整体迁移（优先） |
| `/var/log/messages` | CentOS 综合系统日志 | 若不整体迁移 `/var/log`，可单独迁 |
| `/var/log/secure` | 登录认证与安全审计 | 建议迁 |
| `/var/log/cron` | 定时任务日志 | 建议迁 |
| `/var/log/maillog` | 邮件相关日志 | 按需迁 |
| `/var/log/dmesg` | 内核启动与硬件消息 | 按需迁 |
| `/var/log/audit` | auditd 审计日志 | 建议迁 |
| `/var/log/syslog` | Ubuntu 综合系统日志 | 建议迁 |
| `/var/log/auth.log` | Ubuntu 认证日志 | 建议迁 |
| `/var/log/kern.log` | Ubuntu 内核日志 | 按需迁 |
| `/var/log/nginx` | Nginx 日志 | 建议迁 |
| `/var/log/httpd` | Apache 日志 | 建议迁 |
| `/var/log/tomcat*` | Tomcat 日志 | 建议迁 |

### 7.1.2 业务日志扫描范围

- `/opt`
- `/data`
- `/usr/local`
- `/home`
- 常见模式：`logs/`、`log/`、`*.log`、`catalina.out`、`nohup.out`

### 7.1.3 排除项

- Docker 容器日志：`/var/lib/docker/containers`
- overlay 目录：`/opt/weaver/e-monitor/docker/overlay2`
- 临时目录：`/tmp`、`/run`
- 程序二进制目录、jar 包目录本身

## 7.2 日志迁移原则

- **目录类日志**：优先 `bind mount`
- **单文件日志**：使用软链接
- **父子路径冲突**：不得同时批准，如已批准 `/var/log`，则不再批准 `/var/log/messages`
- **迁移前必须完成人工审核**

## 7.3 日志迁移通用流程

```text
1. 运行发现脚本生成 discovered_logs.tsv
2. 复制为 approved_logs.tsv
3. 人工将 approved 列改为 Y/N
4. 执行 apply 脚本
5. 脚本检查父子冲突并中止风险项
6. rsync 数据到共享盘
7. 原目录/原文件改名为 .bak_时间戳
8. 目录类用 bind mount，单文件类用软链接
9. 写入 migration_state.tsv
10. 验证日志持续写入
```

## 8. `/etc/fstab` 永久挂载配置

## 8.1 分区挂载示例

> 以下 UUID 需以实施现场 `blkid` 实际结果为准。

### 192.168.0.111

```fstab
UUID=<NODE1_PART_UUID>  /filedata/node1  ext4  defaults,noatime,nodiratime  0 2
/filedata/node1/mysql/mysql57_3603  /data/mysql57/data  none  bind  0 0
```

### 192.168.0.3

```fstab
UUID=<NODE2_PART_UUID>  /filedata/node2  ext4  defaults,noatime,nodiratime  0 2
/filedata/node2/mysql/mysql3308    /opt/mysql/mydata/3308/data      none  bind  0 0
/filedata/node2/mysql/weaver3306   /usr/local/weaver_mysql/data     none  bind  0 0
```

### 192.168.0.4

```fstab
UUID=<NODE3_PART_UUID>  /filedata/node3  ext4  defaults,noatime,nodiratime  0 2
/filedata/node3/mysql/mysql57_3603  /data/mysql57/data  none  bind  0 0
```

## 8.2 日志 bind mount 持久化

对目录类日志，按批准清单追加到 `/etc/fstab`，示例：

```fstab
/filedata/node1/logs/system/var_log     /var/log                 none  bind  0 0
/filedata/node2/logs/services/nginx     /var/log/nginx           none  bind  0 0
/filedata/node3/logs/services/tomcat    /opt/tomcat/logs         none  bind  0 0
```

> 单文件日志软链接 **不写 fstab**。

## 9. 分步实施步骤

## 9.1 阶段一：共享盘分区与节点初始化

1. 在 `192.168.0.4` 停止对 `/filedata` 的使用并卸载旧挂载
2. 对 `/dev/sdb` 重新分区为 `sdb1/sdb2/sdb3`
3. 分别格式化为 ext4，并写入 label
4. Node1/Node2/Node3 分别挂载各自分区到 `/filedata/nodeX`
5. 运行各节点初始化脚本，创建标准目录
6. 执行 `mount -a` 验证开机自启正确

## 9.2 阶段二：MySQL 迁移

按系统逐台切换：
1. 三方、安全平台
2. 门户/CAS/泛微（先 3308 再 3306）
3. 对外平台

每次只切一个实例，切完立即验证。

## 9.3 阶段三：日志发现与审核

1. 运行发现脚本
2. 审核 `approved_logs.tsv`
3. 明确每个日志的作用与是否迁移
4. 确认无误后执行迁移脚本

## 9.4 阶段四：验收与清理

1. 连续观察 1~3 个业务高峰周期
2. 验证 MySQL 与日志持续写入共享盘
3. 确认无回滚需求后，再删除本地 `.bak_时间戳` 目录释放空间

## 10. 风险预案

## 10.1 高风险项

### 风险1：将同一 ext4 文件系统三机同时读写
- **风险级别**：高
- **说明**：会造成文件系统损坏风险
- **预案**：严格采用三分区独占模型，不允许三机同挂同一 ext4

### 风险2：Node3 当前整盘直挂 `/filedata`，需重分区
- **风险级别**：高
- **说明**：需要短窗口卸载并重新分区
- **预案**：执行前确认 `/filedata` 上无生产有效数据；脚本先做目录占用和挂载占用检查

### 风险3：Node2 双 MySQL 实例切换顺序错误
- **风险级别**：高
- **说明**：可能引发双实例同时不可用
- **预案**：3308、3306 分两次独立实施，严格一实例一验证

### 风险4：日志目录误迁
- **风险级别**：中
- **说明**：可能迁移无关目录、临时目录或父子路径冲突目录
- **预案**：强制先生成说明清单，人工审核后才可执行；脚本做父子路径冲突校验

### 风险5：迁移后服务权限异常
- **风险级别**：中
- **说明**：MySQL/业务日志目录属主不正确会导致服务启动失败
- **预案**：脚本自动继承原目录属主属组并再次 `chown`

### 风险6：迁移范围与磁盘释放预期不一致
- **风险级别**：中
- **说明**：从现场数据看，部分机器 `/opt` 占用非常高，本次不迁移程序安装目录，因此系统盘释放空间取决于 MySQL 与日志实际占用
- **预案**：先执行 `du` 基线统计；方案验收按“数据库与日志迁移完成”口径，不把程序目录纳入本次范围

## 11. 一键回滚方案

## 11.1 回滚触发条件

任一条件满足即可回滚：
- MySQL 启动失败
- MySQL 启动后读写异常
- 业务日志停止写入
- 系统日志异常
- 挂载失败或开机自启失败
- 业务侧验证不通过

## 11.2 回滚原则

- 按 `migration_state.tsv` 逆序回滚
- 先停止受影响服务，再卸载 bind mount / 删除软链接
- 恢复原始 `.bak_时间戳` 目录/文件
- 删除对应 `/etc/fstab` 追加项
- 验证恢复成功后再退出

## 11.3 回滚流程

```text
1. 停止 MySQL / 受影响业务服务
2. 逆序读取 migration_state.tsv
3. bind mount 项：umount 原路径 -> 恢复 .bak 目录
4. symlink 项：删除软链接 -> 恢复 .bak 文件
5. 清理 /etc/fstab 中本次追加记录
6. 启动 MySQL / 服务
7. 验证原地恢复成功
```

## 12. 操作注意事项

1. **必须先在 Node3 执行共享盘分区初始化**，再分别执行 Node1/Node2/Node3 挂载脚本。
2. `/dev/sdb` 重分区前必须确认旧 `/filedata` 中无正式业务数据。
3. MySQL 切换期间禁止写业务高峰变更。
4. 日志迁移必须先审核 `approved_logs.tsv`，严禁直接跑 apply 脚本。
5. 同一父子路径只允许批准一个，防止 bind 嵌套冲突。
6. 回滚成功前，不得删除任何 `.bak_时间戳` 本地目录。
7. 验收通过后，再手工删除 `.bak_时间戳` 目录以释放系统盘空间。

## 14. 最终结论

在你给出的真实环境下，要做到“**生产可用** + **零业务代码改造** + **共享盘承载 MySQL/日志**”，正确方式不是三机同挂同一 ext4，而是：

- **共享盘三分区，节点独占**
- **MySQL 用 bind mount 回挂原路径**
- **日志先发现、带说明清单、人工确认后批量迁移**
- **全流程可回滚**

该方案满足：
- 不改业务代码
- 不改业务日志写入配置
- 原路径无感知
- 支持开机自启
- 支持分批实施
- 支持一键回滚
