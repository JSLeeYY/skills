# 服务器磁盘治理方案说明

## 一、当前情况

目前三套核心业务系统分别运行在 3 台服务器上，系统盘使用率已整体偏高：

| 业务系统 | 服务器IP | 操作系统 | 当前系统盘使用率 | 备注 |
|---|---|---|---:|---|
| 三方、安全平台 | 192.168.0.111 | CentOS 7.9 | 88% | MySQL 5.7.36，非 systemd |
| 门户、CAS单点登录、泛微 | 192.168.0.3 | Ubuntu 18.04.6 | 89% | 双 MySQL 实例，非 systemd |
| 对外平台 | 192.168.0.4 | CentOS 7.9 | 93% | 当前 `/dev/sdb` 已挂载 `/filedata` |

现场同时具备一块 2T 共享云盘 `/dev/sdb`，当前为整盘 `ext4` 文件系统。三套业务涉及 4 个 MySQL 数据目录，以及大量业务日志、系统日志，核心压力都集中在系统盘。

从现状看，问题不是“磁盘快满了要不要整理”，而是“系统盘持续高位运行，已经影响生产安全边际”。尤其是对外平台系统盘使用率已达到 93%，继续增长将直接压缩数据库写入、日志落盘、故障排查和后续运维操作空间。

其中，门户、CAS、泛微所在的 `192.168.0.3` 服务器，除了 MySQL 和日志占用空间外，泛微软件本身安装部署后已经占据了本地磁盘较大比例。由于本次治理方案不包含 `/opt` 等程序安装目录迁移，因此仅靠共享盘承接数据库和日志，不能从根本上解决该节点的本地磁盘容量问题。对该服务器而言，磁盘扩容应作为本次治理工作的前置配套措施，同步纳入实施安排。

## 二、为什么要做

这次工作本质上是一次生产稳定性治理，主要原因有四点：

1. 系统盘空间持续高位运行，存在数据库写入失败、日志停止生成、服务异常中断等风险。
2. 当前共享盘是整盘 `ext4` 形态，`ext4` 不是集群文件系统，不能让三台服务器同时以读写方式直接挂载使用，否则存在元数据损坏和文件系统损坏风险。
3. 现网 MySQL 实例均为非 `systemd` 管理，数据目录路径分散，若继续维持现状，后续扩容、迁移、故障恢复的复杂度都会越来越高。
4. 业务希望在不改代码、不改原有业务路径的前提下完成治理，因此需要一套既能释放系统盘压力、又尽量不影响应用配置的实施方案。
5. 门户、CAS、泛微所在服务器由于泛微软件安装目录本身占用较大，本地磁盘容量已经偏紧；考虑到本次又明确不迁移程序安装目录，因此该节点必须先完成磁盘扩容，再实施后续共享盘治理，才能保证治理效果完整落地。

## 三、准备怎么干

### 3.1 总体思路

总体策略是“共享盘分区独占、原路径保持不变、分批切换、全程可回滚”。

具体做法如下：

1. 将共享云盘 `/dev/sdb` 重建为 3 个独立分区。
2. 每台服务器只挂载自己的分区，避免多机同时读写同一个 `ext4`。
3. 各节点统一挂载到 `/filedata/nodeX`。
4. MySQL 数据目录和日志目录迁移到共享盘后，通过 `bind mount` 或软链接挂回原路径，保证业务侧路径不变、配置不变。

### 3.2 分区规划

| 分区 | 对应服务器 | 建议容量 | 挂载点 |
|---|---|---:|---|
| `/dev/sdb1` | 192.168.0.111 | 500G | `/filedata/node1` |
| `/dev/sdb2` | 192.168.0.3 | 800G | `/filedata/node2` |
| `/dev/sdb3` | 192.168.0.4 | 其余全部 | `/filedata/node3` |

如现场确认 Node1 或 Node3 数据规模更大，可调整为 `600G / 800G / 其余`，但原则不变。

### 3.3 迁移范围

本次纳入迁移的内容：

- MySQL 数据目录
- 宿主机业务日志
- 系统运行日志

本次明确不纳入迁移的内容：

- Docker 容器日志
- `/opt` 下程序安装目录
- 业务代码改造
- 应用配置重构

这意味着本次工作的目标是“把最占空间、最影响稳定性的数据库和日志迁到共享盘”，而不是对整台服务器做全面瘦身。

基于这一边界，`192.168.0.3` 服务器需要增加一项前置动作：先对本地磁盘做扩容，解决泛微软件安装目录长期占用空间的问题；随后再实施 MySQL 和日志上共享盘。换言之，该节点不是单纯做共享盘治理，而是“本地扩容 + 共享盘治理”两步同时统筹。

### 3.4 各系统落点

| 业务系统 | 原数据目录 | 迁移后共享盘目录 |
|---|---|---|
| 三方、安全平台 | `/data/mysql57/data` | `/filedata/node1/mysql/mysql57_3603` |
| 门户/CAS/泛微 3308 | `/opt/mysql/mydata/3308/data` | `/filedata/node2/mysql/mysql3308` |
| 门户/CAS/泛微 3306 | `/usr/local/weaver_mysql/data` | `/filedata/node2/mysql/weaver3306` |
| 对外平台 | `/data/mysql57/data` | `/filedata/node3/mysql/mysql57_3603` |

日志目录按“业务日志”和“系统日志”两类统一沉淀到各自节点的 `/filedata/nodeX/logs/` 下管理。

### 3.5 前置条件与实施主体

本次工作建议按“先扩容、后治理”的顺序推进，其中：

1. 对 `192.168.0.3` 节点，先完成本地磁盘扩容，再执行共享盘治理，此事针对泛微软件本身的文件就比较大。
2. 对三台服务器的共享盘重分区、挂载初始化、MySQL 迁移、日志迁移、验证和回滚演练，原则上由合作的软件公司承担实施工作，我司负责变更协调、现场配合、业务验证和结果验收。
3. 整体时间安排上，建议将本次工作作为三期开发启动前的基础环境治理事项，要求在我司三期开发工作正式开始前先行完成，需软件公司来实施完成此项，同时避免开发启动后再叠加基础环境改造风险。

## 四、实施方式与安排

### 4.1 实施原则

为控制风险，现场执行遵循以下原则：

1. 一次只动一台服务器。
2. 一次只切一个核心服务。
3. `192.168.0.3` 节点先做本地磁盘扩容，再做共享盘准备、MySQL 和日志迁移。
4. 每一步完成后立即验证，验证不过立即回滚，不进入下一步。
5. 所有原目录都保留 `.bak_时间戳` 备份，验收通过前不删除。

### 4.2 实施步骤

整个实施建议分四阶段：

**第一阶段：门户/CAS/泛微节点本地扩容**

- 先对 `192.168.0.3` 服务器实施本地磁盘扩容。
- 扩容完成后确认操作系统识别、文件系统扩展和可用空间恢复正常。
- 扩容通过后，再进入后续共享盘治理阶段。

**第二阶段：共享盘基础准备**

- 在 `192.168.0.4` 上完成共享盘重分区和 `node3` 初始化。
- 在 `192.168.0.111` 上挂载 `node1` 分区并初始化目录。
- 在 `192.168.0.3` 上挂载 `node2` 分区并初始化目录。

**第三阶段：MySQL 迁移**

- 先迁三方、安全平台 MySQL。
- 再迁门户/CAS/泛微 `3308` 实例。
- `3308` 验证通过后，再迁 `3306` 实例。
- 最后迁对外平台 MySQL。

**第四阶段：日志迁移**

- 先由脚本自动发现候选日志目录和文件。
- 再人工审核形成 `approved_logs.tsv`。
- 审核通过后分批迁移。
- 每批迁移后立即验证业务访问和日志持续写入情况。

### 4.3 对业务的影响

本次实施不是长时间停机迁移，而是“短暂停服切换”：

- 共享盘准备阶段主要影响运维操作，不直接影响业务访问。
- MySQL 迁移阶段需要短时停库切换。
- 日志迁移阶段风险相对可控，但必须先审核后执行，避免误迁。

换句话说，这次不是“大范围停机”，而是“多次小窗口、逐项确认、逐项放行”的实施方式。

## 五、主要风险点及控制措施

### 风险一：三台服务器同时读写同一个 `ext4`

这是最高风险项。若继续按“一块整盘 ext4 多机直接共用”的方式实施，可能造成文件系统损坏，属于生产不可接受风险。

控制措施：必须改为“三分区独占模型”，每台服务器只使用自己的分区。

### 风险二：对外平台现有 `/filedata` 上存在遗留生产数据

由于 Node3 当前已将 `/dev/sdb` 挂载到 `/filedata`，如果直接重分区而未核实现有数据，存在误删风险。

控制措施：重分区前必须确认旧 `/filedata` 无正式生产数据，再进入实施。

### 风险三：门户/CAS/泛微双 MySQL 实例切换失败

Node2 同时承载 `3308` 和 `3306` 两个 MySQL 实例，复杂度明显高于其他节点。

控制措施：严格按“先 3308、后 3306”的顺序串行迁移，前一个实例未验证通过，不进入下一个实例。

### 风险四：日志误迁或迁移范围失控

日志目录数量多、分布散，若直接迁移，容易把无关目录、父子重叠目录一并迁入，影响系统稳定性。

控制措施：先自动发现，再人工审核；脚本同时校验父子路径冲突，Node2 明确排除 Docker 路径。

### 风险五：权限异常导致服务无法写入

迁移后如果目录属主属组处理不当，可能出现数据库无法启动、日志无法持续写入等问题。

控制措施：迁移脚本继承原目录权限，并在切换后立即校验进程、端口、挂载和写入状态。

### 风险六：领导对“释放空间”预期过高

本次不迁移 `/opt` 程序安装目录，也不做应用重构，因此系统盘释放空间主要来自 MySQL 数据和日志，不应理解为“系统盘所有内容都迁走”。

控制措施：验收口径要明确为“数据库和日志已迁入共享盘，生产风险得到降低”，不对安装目录瘦身做超范围承诺。

## 六、风险兜底与回滚机制

本方案不是只考虑“怎么迁”，同时也明确设计了“迁坏了怎么办”：

1. 触发条件明确。出现 MySQL 无法启动、页面不可用、登录失败、数据读写异常、日志停止生成、挂载丢失、权限异常等任一情况，立即回滚。
2. 回滚路径清晰。按 `migration_state.tsv` 记录逆序回滚，先卸载挂载点或删除软链接，再恢复原始目录备份。
3. 回滚分类可控。支持全量回滚，也支持仅回滚 MySQL 或仅回滚日志，避免扩大影响面。

这意味着本次实施具备“可验证、可中止、可回退”的完整闭环。

## 七、预期效果

实施完成后，预期可达到以下目标：

1. 三台服务器系统盘压力明显下降，尤其是数据库和日志不再持续挤占系统盘空间。
2. 三套业务系统的数据库和日志统一落入共享盘，便于后续运维管理、排查和扩容。
3. 业务原有路径保持不变，减少应用侧改造风险。
4. 形成标准化脚本、SOP、检查清单和回滚方案，后续可重复执行、可审计、可交付。

## 八、建议领导关注和协调事项

为确保实施顺利，建议领导层面重点协调以下事项：

1. 同意按“单台、单服务、短暂停服”的方式组织实施窗口。
2. 同意将 `192.168.0.3` 节点本地磁盘扩容作为前置任务先行实施，避免泛微程序安装目录持续挤占本地磁盘空间。
3. 明确由合作的软件公司承担本次实施工作，我司负责组织协调、业务验证和验收把关。
4. 明确业务确认人，确保每次切换后能及时完成登录、页面、数据库连接和关键交易验证。
5. 明确时间要求：原则上在我司三期开发工作正式开始前完成本次治理，避免开发期叠加基础环境变更。
6. 统一验收口径：本次目标是完成节点扩容及数据库、日志上共享盘，不把范围扩大到程序安装目录改造和代码改造。
7. 要求现场严格执行“验证不过即回滚”的纪律，避免连续推进放大风险。

## 九、汇报结论

综合判断，本次服务器磁盘治理工作具备实施必要性，也具备实施条件。

一方面，三台服务器系统盘已处于高位运行状态，继续拖延会放大生产风险；另一方面，现有方案已经明确了技术路线、实施顺序、风险控制和回滚机制，能够在不改业务路径、不大面积停机的前提下完成治理。

建议按既定方案尽快安排实施窗口，由合作的软件公司组织实施，先完成 `192.168.0.3` 节点本地磁盘扩容，再完成共享盘分区独占和 MySQL/日志迁移，并在我司三期开发工作正式启动前优先落地，先把当前最核心的基础环境风险降下来。
