# 综合管理_IT需求审批流表单与台账模板

## 1. 编写依据

本稿仅依据 [2026.03.04职能部门需求审批及决策管理办法.docx](/d:/DevelopmentLocation/agent%20skill/skills/word_project/2026/ITSM规范说明文档/2026.03.04职能部门需求审批及决策管理办法.docx) 编撰。

- 本稿的作用是把领导提供的管理办法拆成 `综合管理` 平台可配置的实施稿。
- 如本稿与原办法有任何不一致，以原办法为准。
- 原办法没有附模板的内容，本稿只做“按原文拆字段”，不自行新增制度口径。

## 2. 编写方式

按审批流拆分，每个审批流固定写 4 项：

1. 模板
2. 字段
3. 审批节点
4. 台账

表单布局建议：

1. 页头放 `业务单号 + 当前状态`。
2. 第一块放 `申请信息区`。
3. 第二块放 `部门负责人审批区`。
4. 第三块放 `可行性评估区`。
5. 第四块放 `必要性审批区`。
6. 最后放隐藏的系统控制字段。

### 4.3 审批节点

1. 提出部门填写 `数字化转型需求申请表`
2. 部门负责人审批确认
3. 提交 `科研运营中心(数字信息条线)` 初审
4. `科研运营中心(数字信息条线)` 在同一张表的“可行性评估区”内于 5 个工作日内完成评估，并形成《需求可行性评估报告》输出件
5. 评估结果为 `可行` 或 `需调整后可行` 的，由需求部门提交分管领导做必要性审批
6. 分管领导在 3 个工作日内给出审批意见，意见类型固定为 `同意`、`暂缓`、`否决`

### 4.4 台账

- 原办法对本流未单列正式台账。
- 本流的正式归档件应至少包括：
  - 同一张主表生成的《数字化转型需求申请表》输出件
  - 同一张主表生成的《需求可行性评估报告》输出件
  - 分管领导必要性审批意见
- 如平台需要查询能力，可做过程查询表，但不应冒充原办法正式台账。

### 5.3 审批节点

1. 通过必要性审批的需求，进入预算评估
2. `科研运营中心(数字信息条线)` 在 5 个工作日内完成预算评估，输出 `需求预算评估表`
3. 按正文提交 `采购部负责人` 审核
4. 提交 `财务部负责人` 审核
5. 提交 `需求部门分管领导`
6. 提交 `数字信息分管领导`
7. 提交 `总经理审批`

说明：

- 原办法正文写的是完整审批链路。
- 附件 2 写了 `<=50 万元` 和 `>50 万元` 的字段分支。
- 平台配置时应同时保留“完整审批链路”和“金额条件显示字段”两层控制。

### 5.4 台账

- 原办法对本流未单列正式台账。
- 本流的正式归档件为 `需求预算评估表`。
- 如平台需要统计预算审批状态，可建立内部查询表，但制度名称仍应以附件 2 为准。

## 6. 审批流三：合同签订前基准确认与合同审批衔接流

### 6.1 模板

本流不建议强行做成一张表。

原因：

- 原办法 `2.5` 本身就对应 3 个不同业务对象。
- 这 3 个对象的发起人、审批链、归档时点都不同。
- 因此在泛微里应拆成 3 张表单，而不是一张大杂烩。

建议拆为：

1. `合同签订需求基准确认书`
2. `采购结果审批表`
3. `合同审批表`

### 6.3 审批节点

## 9. 审批流一的系统推荐实现方案：同一主表双分区

本节是基于原办法 `2.1`、`2.2`、`2.3` 给出的系统实现建议。

- 原办法要求的是先后顺序、处理角色、处理时限、输出结果。
- 原办法没有强制要求《数字化转型需求申请表》与《需求可行性评估报告》必须拆成两张独立流程单。
- 因此在 `综合管理` 平台中，推荐做成：`同一条流程 + 同一张主表 + 两个业务分区 + 不同节点权限`。

### 9.1 适用前提

只有在满足以下前提时，才建议采用“同一主表双分区”：

1. 平台支持按节点控制字段可见、可编辑、只读。
2. 平台支持流程分支控制。
3. 平台支持按表单区块或字段组合打印不同输出件。
4. 平台支持记录节点处理人、处理时间、处理意见。

如果以上能力缺一项都没有，再退回“申请表与评估报告拆成两张物理表”的保守方案。

### 9.2 主表结构

建议同一张主表分成 5 个区块：

| 分区 | 填写角色 | 作用 |
| --- | --- | --- |
| A. 申请信息区 | 提出部门 | 对应《数字化转型需求申请表》主体内容 |
| B. 部门负责人审批区 | 部门负责人 | 对应附件 1 中部门负责人意见 |
| C. 可行性评估区 | 科研运营中心(数字信息条线) | 对应《需求可行性评估报告》 |
| D. 必要性审批区 | 需求部门分管领导 | 对应原办法 `2.3` |
| E. 系统控制区 | 系统自动带出 | 编号、状态、当前节点、锁定标记、处理时间等 |

### 9.5 自动锁定规则

1. 发起人提交后，A 区先转只读，除非被退回。
2. 部门负责人退回时，仅 A 区恢复可编辑，B 区保留历史意见只读。
3. 进入 `科研运营中心(数字信息条线)` 评估节点后，A 区、B 区全部锁定。
4. 评估提交后，C 区锁定，不允许后补改评估结论。
5. 进入分管领导审批后，A/B/C 区全部只读，仅 D 区可编辑。
6. 流程结束后，全表只读。

### 9.6 分支规则

#### 9.6.1 部门负责人节点

- `同意提交` -> 进入可行性评估
- `退回修改` -> 退回发起人
- `不同意提交` -> 流程结束

#### 9.6.2 可行性评估节点

- `可行` -> 进入必要性审批
- `需调整` -> 建议仍进入必要性审批，但必须带调整建议
- `不可行` -> 流程结束并反馈提出部门

#### 9.6.3 必要性审批节点

- `同意` -> 进入预算评估与审批流
- `暂缓` -> 流程挂起或结束，状态记为 `暂缓`
- `否决` -> 流程结束，状态记为 `否决`

### 9.7 两份输出件的处理方式

虽然系统内是“一张主表”，但对外输出仍建议保留两份命名成果：

| 输出件名称 | 取数范围 | 生成时点 |
| --- | --- | --- |
| 《数字化转型需求申请表》 | A 区 + B 区 | 部门负责人审批完成后即可打印 |
| 《需求可行性评估报告》 | A 区摘要 + C 区 | 可行性评估完成后打印 |

这样既不破坏原办法中的文书名称，又避免系统里重复建两张单。

### 9.8 推荐结论

对审批流一，推荐采用以下实现口径：

- `流程上`：一条流程
- `表单上`：一张主表
- `结构上`：双主业务分区，外加审批区和系统区
- `控制上`：严格按节点锁字段
- `输出上`：仍保留两份文书名称

不推荐的做法是：

- 把申请信息和评估信息混成一段不分区字段
- 让发起人和评估人都能改同一批字段
- 评估完成后还能回头改申请原文
- 因为系统合并了，就取消《需求可行性评估报告》的独立输出名称
