# AI基础识别功能DIFY详细实现方案

## 1. 编写目的

本文用于响应《招标文件评分项》中“系统设计要求及成熟度”评分标准下关于 AI 功能实现的要求，重点说明本项目 `11.1.29 AI基础识别功能` 的落地方式、实现深度、成熟度体现和风险控制机制。

本文仅聚焦 AI 功能实现部分，目标是把“可以进行智能文档识别，具备基础的信息智能查阅；具备资料查询辅助功能，方便监造人员进行知识查询”这两项评分要求，转写为可交付、可演示、可复核、可运维的 DIFY 私有化实现方案。

## 2. 评分要求理解

结合评分表要求，AI 部分的核心判分点可归纳为以下四项：

1. 具备智能文档识别能力，能够处理扫描件、PDF、资料附件等文档。
2. 具备基础的信息智能查阅能力，能够辅助定位关键页面、关键条款和关键信息。
3. 具备资料查询辅助功能，能够面向监造资料、标准资料、历史案例、培训资料开展检索和查阅。
4. 方便监造人员进行知识查询，且实现方式成熟、可证明、可落地。

因此，本项目 AI 方案不能只停留在“接入大模型”层面，而必须体现以下特征：

1. 有明确的业务输入、处理链路、输出结果和人工复核环节。
2. 有可展示的 DIFY 工作流编排和实际输出成果。
3. 有本地部署和国产化适配能力，保证数据安全和可控性。
4. 有知识库、查询辅助、字段抽取、结果留痕等工程化设计，不是一次性演示。

## 3. 功能定位与建设范围

### 3.1 功能定位

本项目中的 AI 基础识别功能，定位于“辅助识别、辅助抽取、辅助检索、辅助归类、辅助查阅、辅助成稿、人工复核闭环”，不取代业务审批、不替代专业质量判定、不绕开人工复核。

其核心作用是提升监造业务中文档处理效率、资料检索效率、历史案例复用效率和知识查询效率，使监造人员能够更快完成资料理解、风险识别、要点整理和过程文稿编制。

### 3.2 建设范围

本次建设范围包括以下四类能力：

1. 面向扫描件、PDF、技术协议、图纸说明、数据表附件的智能文档识别。
2. 面向长篇技术文件的基础信息智能查阅，包括重点页面定位、重点条款定位、关键信息摘取。
3. 面向资源库、培训库、标准库、历史案例库的资料查询辅助。
4. 面向监造人员日常工作的知识查询辅助，包括标准查询、案例查询、资料引用和问答式查阅。

### 3.3 重点补强的两个功能点

在既有 `11.1.29 AI基础识别功能` 描述基础上，本方案进一步明确以下两个功能点：

1. 可以进行智能文档识别，具备基础的信息智能查阅。
2. 具备资料查询辅助功能，方便监造人员进行知识查询。

### 3.4 风险控制原则

AI 输出结果统一作为辅助结果，不直接进入正式业务数据链。所有关键字段、关键结论、关键控制点和正式交付文稿，必须经过人工确认或人工复核后方可生效。系统保留识别来源、处理过程、输出结果和人工修订痕迹，确保质量管理严肃性和可追责性。

## 4. 国产化与本地部署总体方案

### 4.1 总体原则

为满足项目对数据安全、可控运维和国产化适配的要求，AI 基础识别功能采用“平台本地部署、模型本地部署、知识库本地部署、解析服务本地部署、结果本地留存”的私有化方案。

### 4.2 平台本地部署

1. DIFY 平台采用私有化部署方式，部署在项目内网服务器或专有云资源池内。
2. Workflow、Chatflow、知识库、模型配置、插件服务、文件存储、日志审计均在本地网络环境内运行。
3. 所有文档上传、向量化、检索、问答、结构化输出和 Word 生成过程均不依赖公网。

### 4.3 国产化模型本地部署

本方案明确采用国产化可替代的本地模型能力，推荐如下：

1. 主推理模型可采用本地部署的千问系列模型，作为文档理解、字段抽取、问答生成和终审校验的核心模型。
2. 也可采用本地部署的 DeepSeek 系列模型，作为文档分析、知识问答和结构化生成模型。
3. 向量化模型建议采用本地部署的中文嵌入模型，用于知识库切片向量化。
4. 重排序模型建议采用本地部署的中文 rerank 模型，用于提升知识检索准确率。

在 DIFY 平台内，上述模型可通过本地模型服务方式统一接入。也就是说，DIFY 仅作为编排与应用平台，千问或 DeepSeek 作为内网模型服务提供实际推理能力，满足“DIFY 本地部署、模型本地部署、数据不出域”的要求。

### 4.4 国产化体现方式

为便于在投标文件和答辩中体现国产化，本方案建议明确写入以下表述：

1. AI 编排平台采用本地私有化部署的 DIFY。
2. 大语言模型采用本地部署的千问模型或本地部署的 DeepSeek 模型。
3. 文档解析服务采用本地部署的 PDF 文本提取组件和本地部署的 MinerU 结构化解析服务。
4. 知识库、向量索引、日志审计、文件存储均部署在项目本地环境。
5. 全流程不依赖公网外部推理接口，满足数据安全与国产化应用要求。

## 5. 基于 DIFY 的总体实现架构

### 5.1 总体架构思路

本项目采用 DIFY 作为 AI 能力编排平台，将 AI 基础识别功能拆分为两条主流程：

1. `工作流 A：智能文档识别与基础信息智能查阅流程`
2. `工作流 B：资料查询辅助与知识查询流程`

两条流程共享同一套本地模型和本地知识库能力，但面向的业务目标不同：

1. 工作流 A 偏“文档输入驱动”，用于把上传的技术协议、扫描件、PDF、附件资料转化为可查阅、可抽取、可结构化的业务结果。
2. 工作流 B 偏“问题输入驱动”，用于让监造人员针对标准、案例、流程、设备资料进行知识检索和问答式查阅。

### 5.2 总体架构组成

整体架构建议由以下模块构成：

| 模块层 | 建设内容 | 作用 |
| --- | --- | --- |
| 应用入口层 | DIFY Workflow、DIFY Chatflow、内部业务入口页面 | 为监造人员提供文档上传、资料查询、知识问答入口 |
| 编排控制层 | 开始节点、变量节点、条件分支、LLM 节点、HTTP 请求节点、知识检索节点、输出节点 | 负责业务流程编排、路由和结果汇聚 |
| 模型能力层 | 本地部署千问模型或本地部署 DeepSeek 模型 | 负责文档理解、字段抽取、问答生成、终审校验 |
| 文档解析层 | PDF 文本提取、本地 MinerU 解析服务 | 负责 OCR、文本抽取、Markdown 结构化转换 |
| 知识服务层 | 标准库、案例库、培训库、资源库、向量索引、元数据过滤 | 负责资料查询辅助和知识查询 |
| 结果输出层 | JSON 结构化结果、监理大纲 Word、问答结果、引用来源、人工复核界面 | 负责结果展示、下载、复核和归档 |
| 安全审计层 | 账号权限、操作日志、处理留痕、人工确认记录 | 负责安全可控和责任追溯 |

### 5.3 内网部署逻辑

建议采用如下内网部署逻辑：

`监造人员/业务系统 -> 本地 DIFY -> 本地模型服务（千问或 DeepSeek） -> 本地 MinerU/PDF 解析服务 -> 本地知识库/向量库/文件存储 -> 人工复核 -> 正式业务链`

该部署方式的关键价值在于：

1. 上传资料不出内网。
2. 模型推理不依赖外部云接口。
3. 敏感文档、历史案例和标准条款可在本地知识库中受控管理。
4. 所有识别、查询、生成结果均可留痕和复核。

## 6. 现有归档材料所体现的已实现链路

基于当前归档目录中的 `Dify工作流-监理大纲-1.png`、`Dify工作流-监理大纲-2.png` 以及两份 AI 生成的监理大纲样例文档，可以确认当前已具备一条可落地的 DIFY 实现链路，而不是停留在概念层。

### 6.1 现有工作流已体现的关键节点

归档工作流已体现如下核心节点：

1. `开始`
2. `PDF文本提取`
3. `MINERU上传文件`
4. `解析上传路径`
5. `MINERU提交转换`
6. `解析MINERU事件ID`
7. `MINERU读取结果`
8. `解析MINERU MARKDOWN`
9. `关键页定位`
10. `生成文档画像`
11. `工程风险参数JSON生成`
12. `参数化减法终审校验`
13. `JSON规范化`
14. `生成监理大纲 WORD`
15. `返回结果`

### 6.2 现有实现链路说明

该链路已经体现出较成熟的工程思路：

1. 先通过 `PDF文本提取` 获取原始输入文档中的可读文本。
2. 同时通过本地 `MinerU` 服务将 PDF 进一步转化为结构化 Markdown。
3. 对长文档执行 `关键页定位`，优先缩小需要重点理解和处理的页面范围，避免全量解析成本过高或大文档识别不稳定。
4. 将关键页信息、Markdown 结果和 PDF 文本融合成“文档画像”，形成后续结构化抽取的统一输入。
5. 通过本地大模型节点生成工程控制所需的结构化 JSON 参数。
6. 通过终审校验节点检查字段完整性、事实一致性、模板可用性和闭环逻辑。
7. 将规范化后的 JSON 回填到 Word 模板，生成监理大纲等项目文稿。

从现有归档截图可以进一步看出，`工程风险参数JSON生成`、`参数化减法终审校验` 等关键节点已经采用千问模型节点进行处理。这说明当前链路本身就具备沿用国产化大模型路线的落地基础；在项目实施中，可继续采用本地部署的千问模型，也可按甲方环境统一切换为本地部署的 DeepSeek 模型，而无需改变 DIFY 主体编排方式。

归档中的两份 `监理大纲` 样例文档已能体现以下成熟度特征：

1. 已能自动形成完整的文档目录和标准章节结构。
2. 已能识别并回填项目名称、设备名称、位号、材质、规格型号等关键字段。
3. 已能提炼制造风险点、标准依据、监造范围和检试验计划。

### 6.4 归档中已实现方案的实际实现过程

从归档中的 DIFY 工作流截图和生成成果可以看出，我司并非仅进行了方案设计，而是已经完成了一套可运行的 AI 文档处理方案，其实际实现过程可概括为以下步骤：

1. 业务人员上传技术协议 PDF 或相关资料附件，并填写项目提示信息。
2. 系统先对原始 PDF 执行文本提取，获得全文可读文本。
3. 系统同步调用本地 MinerU 解析服务，将原始 PDF 转换为结构化 Markdown。
4. 系统对长文档进行关键页定位，优先识别参数页、材质页、检试验要求页、交付资料页等重点内容。
5. 系统将 PDF 文本、Markdown 结构化结果和关键页结果融合为统一的“文档画像”对象。
6. 系统调用本地部署的国产化大模型，对文档画像执行工程风险参数抽取，形成结构化 JSON。
7. 系统再通过终审校验节点，对抽取结果进行字段完整性、事实一致性、逻辑闭环性和模板可用性校核。
8. 系统将规范化后的 JSON 自动回填到 Word 模板，生成项目化监理大纲初稿。
9. 业务人员对生成结果进行人工复核、修订和确认，最终形成可继续使用的正式业务文稿。

上述过程说明，归档中的方案已经完整跑通了“资料输入 -> 文档识别 -> 重点查阅 -> 结构化抽取 -> 文稿生成 -> 人工复核”的处理闭环，不是单点演示，也不是只停留在模型问答层面。

## 7. 工作流 A：智能文档识别与基础信息智能查阅

### 7.1 功能目标

工作流 A 用于响应评分项中的“智能文档识别”和“基础信息智能查阅”要求，面向以下业务场景：

1. 上传技术协议、扫描件、PDF、图纸说明、数据表附件。
2. 自动识别文档中的文本内容和结构信息。
3. 自动定位关键页面、关键条款和关键参数。
4. 输出结构化结果，供监造人员快速查阅和人工复核。

### 7.2 支持的输入类型

| 输入类型 | 典型内容 | 系统处理方式 |
| --- | --- | --- |
| 扫描件 | 扫描版协议、扫描版检验记录 | OCR + 文本抽取 |
| PDF 文档 | 技术协议、制造文件、检测计划 | 文本提取 + MinerU Markdown 转换 |
| 图纸说明附件 | 图纸说明页、工艺说明页 | 文本抽取 + 关键页定位 |
| 数据表附件 | 设备清单、参数表、试验表 | 表格文本识别 + 字段抽取 |

### 7.3 DIFY 节点级设计

建议按以下节点进行设计和实现：

| 节点名称 | 节点类型 | 主要输入 | 主要输出 | 设计目的 |
| --- | --- | --- | --- | --- |
| 开始 | Start | `input_pdf`、`standard_reference`、`project_hint` | 输入变量 | 接收上传文档及补充说明 |
| PDF文本提取 | 文档提取/工具节点 | 原始 PDF | 可读文本 | 获取全文文本，作为后续查阅基础 |
| MINERU上传文件 | HTTP Request | 原始 PDF | 上传结果 | 将文件提交到本地 MinerU 服务 |
| 解析上传路径 | 代码/变量节点 | 上传结果 | 文件路径 | 解析 MinerU 服务返回信息 |
| MINERU提交转换 | HTTP Request | 文件路径 | 任务提交结果 | 发起 Markdown 转换任务 |
| 解析MINERU事件ID | 代码节点 | 任务提交结果 | `event_id` | 用于后续轮询读取结果 |
| MINERU读取结果 | HTTP Request | `event_id` | Markdown 流结果 | 获取结构化解析结果 |
| 解析MINERU MARKDOWN | 代码节点 | Markdown 结果 | 正文、标题、表格片段 | 将 Markdown 转化为后续可处理文本 |
| 关键页定位 | LLM/规则节点 | 文本抽取结果 | 关键页清单、关键段落 | 找出应重点核查的页面和条款 |
| 生成文档画像 | 代码节点 | PDF文本、Markdown、关键页结果 | 统一画像对象 | 形成后续结构化抽取的融合输入 |
| 工程风险参数JSON生成 | LLM 节点 | 文档画像 | 初版 JSON | 提取项目、设备、材质、标准、风险点等字段 |
| 参数化减法终审校验 | LLM 节点 | 初版 JSON | 校核后 JSON | 审核字段事实一致性、闭环性、模板适用性 |
| JSON规范化 | 代码节点 | 校核后 JSON | 标准 JSON | 统一字段格式，满足接口和模板要求 |
| 生成监理大纲 WORD | 插件/工具节点 | 标准 JSON | Word 文件 | 形成可下载、可复核的文稿成果 |
| 返回结果 | Output | Word 文件、文本、JSON | 页面结果/API 输出 | 把结果返回给用户或上层系统 |

### 7.4 关键处理逻辑

#### 7.4.1 双通道识别

为提升识别稳定性，采用“双通道识别”方式：

1. 一路对 PDF 做直接文本提取，保证全文可搜索、可定位。
2. 一路对 PDF 做 Markdown 结构化转换，保证标题、表格、段落结构可被模型利用。

两路结果在“文档画像”阶段融合，避免单一解析方式失败时导致整体不可用。

#### 7.4.2 大文档关键页策略

对于页数较多、内容冗长的技术协议，不建议直接全量粗放处理，而是通过 `关键页定位` 节点先识别：

1. 设备参数页
2. 材质页
3. 检试验要求页
4. 焊接和无损检测要求页
5. 压力试验和泄漏试验页
6. 包装、防护、交付资料页

然后对关键页做重点理解和结构化提取。这样既能提高处理效率，也能减少无关内容干扰模型判断。

#### 7.4.3 基础信息智能查阅

该流程不只是“提取字段”，还要支持查阅辅助，因此在结构化结果中应至少保留以下信息：

1. 关键字段值
2. 关键字段来源页码或来源段落
3. 重点条款摘要
4. 风险点摘要
5. 引用标准清单

这样监造人员能够快速看到“答案是什么”和“答案来自哪里”，符合“基础信息智能查阅”的评分要求。

#### 7.4.4 结构化输出

建议结构化 JSON 至少包含以下字段组：

1. 项目基础信息：项目名称、设备名称、位号、数量、设备类别。
2. 设备技术信息：主体材质、规格型号、设计寿命、关键制造参数。
3. 标准依据：适用的国家标准、行业标准、技术附件依据。
4. 风险控制信息：关键风险点、重点控制工序、重点检试验项目。
5. 文稿生成信息：标题、章节内容、表格回填参数、备注说明。

### 7.5 典型输出结果

工作流 A 可输出以下成果：

1. 文档识别结果摘要页。
2. 关键字段清单。
3. 关键页定位结果。
4. 风险参数 JSON。
5. 监理大纲 Word 草稿。
6. 供人工复核的来源页码、来源片段和引用依据。

## 8. 工作流 B：资料查询辅助与知识查询

### 8.1 功能目标

工作流 B 用于响应评分项中的“资料查询辅助”和“知识查询”要求，面向监造人员的日常查阅场景，提供问答式、检索式、引用式的知识服务能力。

### 8.2 知识库建设范围

知识库建议至少包含以下内容：

1. 监造标准库：国家标准、行业标准、企业适用规范、技术附件模板。
2. 历史案例库：已完成项目的监造大纲、问题闭环单、质量案例、风险清单。
3. 培训资料库：监造流程培训材料、岗位培训资料、常见问题解答。
4. 资源资料库：设备资料、供方资料、常用表单、检查项模板。

### 8.3 知识库元数据设计

为提升查询精度，建议为每条知识切片建立元数据标签，例如：

| 标签字段 | 示例 |
| --- | --- |
| 项目类型 | 石化、煤化工、硅材料、压力容器 |
| 设备类型 | 换热器、塔器、容器、管道附件 |
| 业务阶段 | 方案、制造、检验、出厂、售后 |
| 资料类别 | 标准、案例、培训、模板、技术协议 |
| 专业分类 | 材料、焊接、无损检测、热处理、压力试验 |
| 适用对象 | 监造工程师、项目经理、管理员 |

### 8.4 DIFY Chatflow/Workflow 设计

建议采用 DIFY 的知识检索能力构建知识查询流程，节点设计如下：

| 节点名称 | 节点类型 | 主要作用 |
| --- | --- | --- |
| 用户输入 | User Input | 接收监造人员的查询问题、关键词或上传资料 |
| 问题分类 | LLM 节点 | 判断属于标准查询、案例查询、培训查询、资料查询还是综合问答 |
| 条件分支 | Condition | 根据问题类型决定检索范围和响应策略 |
| 知识检索 | Knowledge Retrieval | 从标准库、案例库、培训库、资源库检索相关内容 |
| 结果重组 | LLM/代码节点 | 对检索片段进行归并、去重和结构化整理 |
| 答案生成 | LLM 节点 | 基于检索结果形成简洁、可引用的问答回复 |
| 引用输出 | Answer/Output | 返回答案、出处、关联资料和推荐文档 |

### 8.5 典型查询场景

工作流 B 支持以下典型场景：

1. 输入“换热器管板堆焊需要关注哪些风险点”，系统返回标准依据、历史案例和控制建议。
2. 输入“某型号换热器常见检验见证点有哪些”，系统返回控制点和监造记录要点。
3. 输入“类似项目是否有可复用监理大纲”，系统返回相关历史案例和文稿模板。
4. 输入“压力试验、氦检漏、酸洗钝化相关条款在哪些资料里”，系统返回条款出处和对应资料。

### 8.6 查询结果输出要求

为体现“方便监造人员进行知识查询”，查询结果建议至少包含：

1. 直接答案。
2. 引用来源。
3. 相关资料标题。
4. 关联案例或关联标准。
5. 建议进一步查看的原始资料。

如果查询内容涉及关键业务判断，系统应提示“以下为辅助结果，请结合原文和专业人员复核”。

## 9. 数据与知识库设计

### 9.1 切片策略

建议采用“按标题层级 + 按表格块 + 按重点条款”组合切片方式：

1. 标准类文档按章节、条款号切片。
2. 技术协议按标题、页码、表格块切片。
3. 案例类文档按项目、设备、问题类型、处理措施切片。
4. 培训资料按知识点切片。

### 9.2 检索策略

建议采用以下组合检索策略：

1. 语义检索，用于理解“意思相近”的查询。
2. 关键词检索，用于提升专业术语、位号、标准编号等精确命中率。
3. 元数据过滤，用于按项目类型、设备类型、资料类别缩小范围。
4. 重排序，用于把最相关片段排在前面。

### 9.3 结果可信度设计

建议为每次查询和识别结果保留以下信息：

1. 来源文档名称。
2. 来源页码或来源片段。
3. 检索命中时间。
4. 模型生成摘要。
5. 人工复核状态。

## 10. 人工复核与风险控制机制

### 10.1 人工复核闭环

本方案坚持“AI 辅助、人工确认”的控制原则，建议设置如下闭环：

1. AI 先输出识别结果、查询结果或文稿草稿。
2. 监造人员进行人工核对、补充和修正。
3. 经确认后的结果方可进入正式文档、正式业务记录或正式归档。
4. 系统记录 AI 初稿、人工修改稿和最终确认稿。

### 10.2 重点风险控制

需重点防范以下风险：

1. 扫描件识别错误导致字段偏差。
2. 长文档中非关键内容干扰模型判断。
3. 历史案例引用不准确导致知识误用。
4. AI 生成结果未经人工审核直接流入正式业务。

对应控制措施如下：

1. 保留原文来源页和来源片段。
2. 对大文档使用关键页定位策略。
3. 对知识查询结果显示引用出处。
4. 对正式输出文稿设置人工确认状态。

### 10.3 安全与审计

本方案建议至少保留以下审计信息：

1. 谁上传了什么资料。
2. 谁发起了哪次查询。
3. 哪个模型参与了本次处理。
4. 输出结果是什么。
5. 谁完成了人工确认。
