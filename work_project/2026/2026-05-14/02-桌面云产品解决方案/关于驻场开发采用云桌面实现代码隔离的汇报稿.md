# 关于驻场开发采用云桌面实现代码隔离的汇报稿

## 一、事项背景

为降低外部软件公司驻场开发期间的代码泄露风险，拟要求供应商开发人员在我司现场办公时，统一使用我司控制的云桌面开展开发工作，不允许在其个人电脑或自带终端上保留项目代码、开发环境、测试资料及相关数据。项目代码仓库、开发环境、测试环境、中间件及相关资料，原则上全部部署在我司控制的云桌面体系及配套内网环境中，以实现“开发在云端、数据留在公司、终端不落代码”的管理目标。

目前供应商提交了 [桌面云产品解决方案.xlsx](</D:/DevelopmentLocation/agent skill/skills/word_project/2026/2026-05-14/02-桌面云产品解决方案/桌面云产品解决方案.xlsx>)，拟作为本次建设的基础方案。

## 二、总体判断

综合评估认为：

`采用云桌面承载驻场开发，是正确方向，能够明显降低供应商个人电脑直接接触我司代码的风险。`

但同时也应明确：

`当前供应商提交的方案，属于云桌面基础建设方案，可以作为起点，但还不能直接视为满足我司“驻场研发代码隔离闭环管理”要求的最终实施方案。`

原因在于，当前表格主要解决了“桌面集中承载、终端统一接入”的问题，但对于研发型场景必须具备的资源保障、安全管控、数据出口限制、审计留痕和高可用保障，尚未在方案中体现完整。

## 三、方案积极意义

从管理目标看，云桌面模式相较于传统驻场开发，具备以下明显优势：

1. 代码与供应商个人电脑物理隔离。  
开发人员不再直接在个人笔记本中存放项目代码，本地电脑与我司代码之间的直接关系被切断，代码集中保存在我司控制的云桌面及配套环境中。

2. 开发环境集中管理。  
开发所需的前端、后端、数据库连接、测试工具、中间件访问等能力，可统一在云端交付和维护，便于标准化配置和集中管控。

3. 账号权限可统一控制。  
开发人员的访问权限、时间范围、操作范围、项目范围，均可由我司集中授权和回收，避免人员离场后权限残留。

4. 便于审计和追踪。  
若配套日志审计、堡垒机、代码仓库审计和操作留痕机制，可有效提高开发活动的可追溯性。

5. 有利于后续制度化管理。  
云桌面可作为我司外部开发接入的统一标准入口，为后续项目复用、供应商管理和信息安全治理打下基础。

## 四、当前方案存在的主要不足

虽然方案方向正确，但若要实现我司“开发环境全部留在云端、供应商本地不接触代码”的目标，仅靠当前表格所列设备和授权还不够，主要存在以下不足：

### （一）当前方案更偏办公型桌面，不是完整研发型桌面方案

方案当前配置为：

- `1` 台 H3C `UIS 3000 G5` 桌面云服务器
- `1` 套 `H3C Workspace`，含 `10` 个 VDI 授权
- `10` 个云终端
- `10` 台显示器
- `1` 台接入交换机

这套配置可以支撑 `10` 人接入云桌面办公，也可以支持一定程度的轻量开发，但若 `10` 名开发人员长期并发开展前后端分离研发工作，特别是同时进行 `Java 后端编译调试 + Vue 前端启动调试 + 浏览器联调 + 数据库访问 + 日志分析`，当前表格并未充分证明其研发承载能力已经满足要求。

### （二）没有明确每个研发桌面的资源配额

当前方案没有明确每个开发桌面的以下关键参数：

- 分配多少 `vCPU`
- 分配多少 `内存`
- 分配多大 `系统盘`
- 分配多大 `数据盘`
- 使用何种桌面操作系统及授权方式

没有这些内容，就无法确认 `10` 名开发人员在云桌面中是否能稳定完成前后端分离开发，而不仅仅是登录办公。

### （三）没有体现“代码不外流”的关键安全控制项

如果我司的核心诉求是“供应商个人电脑拿不到代码”，则除云桌面本身外，还必须同步落实以下控制：

- 禁止本地磁盘映射
- 禁止文件拖拽与双向文件传输
- 禁止 USB 存储设备重定向
- 禁止本地打印映射
- 禁止剪贴板双向复制
- 限制截屏、录屏、外发通道
- 控制互联网访问和外网下载路径

而当前供应商表格中并未对这些内容进行说明。也就是说，当前方案体现了“桌面放到云上”，但尚未充分体现“数据出口被严格收住”。

### （四）没有明确开发环境和测试环境是否全部纳入我司控制域

若要真正实现本地不落代码，仅有云桌面还不够，还应明确以下内容全部放在我司控制环境内：

- 代码仓库
- 前后端开发环境
- 测试环境
- 数据库
- Redis
- 文件存储
- 制品包和日志文件

如果这些能力仍有一部分放在供应商侧、互联网公共环境或开发人员自带电脑上，则“代码与环境全部留在我司”的目标并未真正实现。

### （五）当前方案为单机架构，存在单点故障风险

当前清单只有 `1` 台桌面云服务器。若该设备发生故障，则 `10` 名开发人员将同时中断工作，开发、测试、联调都会受到影响。

如果我司后续计划把驻场开发全部迁移到云桌面体系中，则单机架构不宜作为长期正式方案，至少应同步考虑：

- 故障恢复机制
- 备份与快照机制
- 关键数据保全
- 后续扩容能力

### （六）不能将“使用云桌面”等同于“绝对拿不到代码”

需要向管理层客观说明：  
采用云桌面后，确实可以显著降低代码被复制到开发人员个人电脑的风险，但若不叠加完整的权限、出口、审计和制度管控，仍不能简单理解为“绝对无法接触或带走代码”。

因此，本方案应理解为“将风险大幅收敛”，而不是“只采购云桌面设备即可自动实现绝对安全”。

## 五、对领导层可形成的明确判断

围绕我司“软件公司驻场开发全部使用云桌面、本地不保留任何项目和开发资料”的目标，建议形成以下判断口径：

### 1. 方向上可以肯定

云桌面集中开发的思路符合我司管理诉求，特别适合用于隔离供应商个人电脑与我司代码、环境之间的直接关系，方向上应予支持。

### 2. 当前表格不能直接作为最终定版方案

供应商当前提交的《桌面云产品解决方案》只能视为基础硬件和接入方案，尚不能直接认定为完整满足我司“驻场研发代码隔离”目标的最终建设方案。

### 3. 必须将“安全管控方案”和“研发承载方案”一并补齐

只有在补齐以下两类内容后，方案才可进入正式实施层面：

- 一类是 `研发承载能力`：保证 `10` 名开发人员能稳定开展前后端分离开发
- 一类是 `安全隔离能力`：保证代码、环境、资料和数据不从云桌面向个人终端外流

## 六、建议补充的实施要求

建议要求供应商在现有表格基础上，进一步补充并承诺以下内容：

### （一）研发资源配置要求

明确每个研发桌面的：

- vCPU 数量
- 内存大小
- 系统盘容量
- 数据盘容量
- 操作系统配置

并说明该资源分配是否能支撑 `10` 人并发前后端开发。

### （二）代码和环境集中部署要求

明确以下内容全部部署在我司控制环境内：

- Git 或代码仓库
- 前端开发环境
- 后端开发环境
- 测试环境
- 数据库和缓存
- 文件存储与日志存储

原则上不得在开发人员个人电脑或供应商外部环境中保留项目源码和开发副本。

### （三）终端出口管控要求

明确关闭或限制以下能力：

- 本地盘符映射
- 文件上传下载
- USB 存储拷贝
- 双向剪贴板
- 本地打印
- 非授权外发通道

必要时结合网络白名单和桌面安全策略统一执行。

### （四）权限与审计要求

明确做到：

- 一人一账号
- 按项目授权
- 按期限授权
- 离场立即回收权限
- 关键操作可审计
- 代码访问可留痕

### （五）高可用与恢复要求

明确说明：

- 单机故障如何恢复
- 桌面快照如何保留
- 数据如何备份
- 后续如何扩容

若作为长期驻场研发平台，建议至少预留冗余或二期扩展能力。
