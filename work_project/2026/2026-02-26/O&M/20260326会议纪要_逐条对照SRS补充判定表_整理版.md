# 20260326 会议纪要对照 SRS 补充文案（全面描述版）

## 1. PECMS 系统

### 1.1 供应商角色与技术服务人员分配

**归属模块**  
PECMS-组织与人员管理

**建议写入 SRS 文案**  
PECMS 需建立完整的“供应商组织—技术服务人员”管理体系，新增供应商角色及其权限边界，并支持管理员按供应商组织维护人员主数据（含入场状态、所属项目范围、有效期、身份标识）。系统应支持人员分配、归属调整、停用/启用、跨供应商迁移等全生命周期管理，且所有动作均需形成可审计轨迹（操作人、操作时间、变更前后值、变更原因）。  
对 O&M 而言，PECMS 是技术服务人员组织关系的主来源系统，O&M 侧不应手工维护同类关系。PECMS 需通过标准接口对外提供可查询、可追溯、可按版本读取的数据能力，用于支撑后续派单、考勤、成本、产值和利润分析，保证跨系统口径一致。

### 1.2 派单过程留痕（含辅助人员）

**归属模块**  
PECMS-派单与过程记录

**建议写入 SRS 文案**  
PECMS 派单模块需对派单参与过程进行全量留痕，留痕对象同时覆盖主责人员与辅助人员，且辅助人员的参与时间段必须作为独立业务事实保存，不得仅以最终状态覆盖历史。系统应记录参与起止时间、角色类型、调整前后关系、调整原因、调整人、调整时间，并支持一次派单中多次参与关系变更的历史串联展示。  
当人员后续发生岗位变更、组织迁移或离岗时，历史派单关系不得被重算或重写。查询侧需支持按派单、按人员、按时间区间反查，确保任何历史统计都能回到“当时谁参与、何时参与、以何角色参与”的原始事实，满足审计与责任追溯。

### 1.3 技术服务考勤线上闭环

**归属模块**  
PECMS-技术服务考勤管理

**建议写入 SRS 文案**  
技术服务考勤管理需在 PECMS 内完成线上闭环，流程为“供应商填报/导入 -> 项目经理审核 -> 区域经理确认 -> 归档生效”。供应商填报时支持批量导入和在线编辑，提交前系统需执行完整校验，包括必填项、时间区间合法性、与派单有效期匹配、与合同/派单关联有效性。  
审批阶段需支持退回、重提、批量处理、意见留痕，并保留每一审批节点的处理人、处理时间、处理结论和说明。归档后，考勤数据需以“人员-派单-合同-月份”为稳定关联键沉淀，供 O&M 进行产值计算与统计，且 O&M 仅可读取已确认归档的数据。

### 1.4 审批后修改机制

**归属模块**  
PECMS-技术服务考勤管理

**建议写入 SRS 文案**  
对于已审批通过的考勤记录，系统应支持“审批后修改”，但修改方式必须采用“变更申请 + 再审批”机制，不允许直接覆盖生效数据。发起变更时需强制填写变更原因，并标注变更范围（人员、时间段、派单、关联合同/派单、成本影响）。  
系统需保留原版本与新版本并建立版本链，支持版本对比查看（字段差异、旧值、新值、变更人、变更时间、审批状态、生效时间）。所有变更必须可追溯、可回放，并在 O&M 拉取时明确读取当前生效版本，避免统计口径漂移。

### 1.5 技术服务成本按人员+月份管理

**归属模块**  
PECMS-技术服务成本管理

**建议写入 SRS 文案**  
技术服务成本按“人员 + 月份”维度管理，供应商负责填报（支持模板导入、批量校验、在线修订），区域经理进行最终确认。填报记录需包含人员标识、供应商标识、期间、成本金额、币种、关联合同/派单、说明信息及凭证附件（如有）。  
确认归档后的数据作为 O&M 成本核算的标准来源，O&M 侧仅可读取，不得反向改写。若后续成本更正，需在 PECMS 发起变更流程并保留历史版本，以保证利润核算、月报、审计口径在任意时间点可回溯一致。

### 1.6 合同字段与 O&M 数据来源关系

**归属模块**  
PECMS-合同管理

**建议写入 SRS 文案**  
PECMS 合同管理需补齐并维护 O&M 计算所依赖的关键字段，包括但不限于合同编号、合同类型、合同单价、有效期间、归属组织及状态信息。对会影响 O&M 指标计算的字段变更，PECMS 需记录版本及生效时间，并提供版本化查询能力。  
O&M 侧读取合同数据时，需记录来源系统、来源版本、拉取时间和关联任务标识；若上游字段发生变更，应触发重算或差异提示机制，确保“同一时间点、同一版本”下各报表计算结果一致。

### 1.7 历史合同数据拆分治理

**归属模块**  
PECMS-历史数据治理

**建议写入 SRS 文案**  
历史合同数据需先治理后入库。治理方案应明确拆分对象、拆分维度（合同、期间、责任主体、业务类型等）、口径定义、字段映射规则、冲突处理原则及复核责任分工。对于无法自动拆分的数据，需进入人工复核池，并保留处理结论。  
治理结果必须保存“原始记录 -> 拆分结果”的映射链路及处理日志，保证 O&M 在做历史统计、对账和审计时，可精确追溯每个结果项的来源、拆分依据与处理过程。

### 1.8 外勤与本部出勤推送至 PECMS

**归属模块**  
PECMS-跨系统出勤数据接入

**建议写入 SRS 文案**  
外勤与本部出勤数据需通过统一接口接入 PECMS，接口规范应明确数据字段、主键规则、时间口径、状态定义、推送频率、重传机制和幂等要求。对于推送失败、重复推送、字段缺失、时间冲突等异常，系统需提供自动拦截和补偿处理能力。  
PECMS 接收后应与派单及考勤数据做一致性校验，不一致数据进入异常池并分配处理责任人，形成“发现问题 -> 修正数据 -> 重新校验 -> 闭环归档”的完整链路。

## 2. O&M 系统

### 2.1 科研经营月报占位列（材料费/制造费）

**归属模块**  
O&M-科研经营月报

**建议写入 SRS 文案**  
科研经营月报中“材料费”“制造费”字段作为业务保留占位列存在，系统不提供自动计算公式，不从其他系统自动回填。该两项由财务在月报填报环节在线录入并留痕，录入后进入 O&M 存储并参与展示与统计。  
未录入时字段应为空值展示，系统不得以 0 自动替代，以避免误导口径。导出报表需保留该字段及口径说明，明确其为“人工填报字段”。

### 2.2 人工费构成口径

**归属模块**  
O&M-科研经营月报

**建议写入 SRS 文案**  
人工费口径统一定义为“正式员工成本 + 劳务派遣成本 + 技术服务成本”。其中前两项沿用既有来源口径，技术服务成本来源于 PECMS 已确认归档的人员成本数据。  
O&M 对技术服务成本仅做读取与按周期聚合，不允许手工改写来源值；如需修正，须回到 PECMS 完成上游修订并重新同步，确保全链路口径一致。

### 2.3 成本小计公式

**归属模块**  
O&M-科研经营月报

**建议写入 SRS 文案**  
科研经营月报“成本小计”采用固定计算口径：`成本小计 = 人工程成本 + 差旅费用 + 固定成本`。系统应在页面字段说明、导出文件脚注、接口文档中统一披露该公式，避免跨部门理解差异。  
当任一分项缺失时，系统应按既定空值策略处理并给出提示，不允许隐式替换导致结果偏差。

### 2.4 毛利金额与毛利率公式

**归属模块**  
O&M-科研经营月报

**建议写入 SRS 文案**  
毛利金额与毛利率的计算口径固定如下：`毛利金额 = 合同额 - 成本小计`，`毛利率 = (合同额 - 成本小计) / 合同额`。系统应统一使用上述公式参与页面展示、导出及接口输出，不得在不同场景采用不同口径。  
当合同额为 0 或空值时，毛利率不参与计算并显示“不可计算”；同时在日志中记录异常口径提示，便于后续数据治理。

### 2.5 付款约定编辑与历史

**归属模块**  
O&M-科研经营月报

**建议写入 SRS 文案**  
付款约定字段需支持单条编辑、批量编辑和历史追溯。任意修改均应记录变更前后值、变更原因、变更人、变更时间、提交方式（单条/批量）及审批状态。  
系统需提供按合同查看变更轨迹能力，支持按时间倒序展示和差异对比，保证财务、项目经理与管理层可在同一页面快速确认付款约定的变更背景与最新状态。

### 2.6 开票/回款台账唯一编号与金额字段

**归属模块**  
O&M-开票回款管控台账

**建议写入 SRS 文案**  
开票/回款管控台账需新增“唯一编号”字段，编号由系统自动生成，具备全局唯一、不可编辑、可检索特性。每条预计开票或预计回款记录均需带编号贯穿生命周期。  
填报场景中应强制包含金额字段，并在后续修改、审批、导出、审计中持续携带该编号。所有行为留痕均按编号关联，确保“每次改动可追、每条记录可查、每笔业务可还原”。

### 2.7 修改说明必填规则

**归属模块**  
O&M-开票回款管控台账

**建议写入 SRS 文案**  
当用户修改预计开票或预计回款记录时，系统必须强制填写“修改原因/修改说明”，未填写不得提交。该字段需在审批流程中完整展示，并进入审计日志与导出记录。  
对于批量修改场景，应支持统一说明与单条补充说明两种模式，确保审批人可准确判断每条记录的变更合理性。

### 2.8 未上平台项目补录能力

**归属模块**  
O&M-非平台项目补录

**建议写入 SRS 文案**  
O&M 需提供未上平台项目的产值与成本补录能力，支持“模板导入 + 在线录入”双通道，满足线下项目线上归集需求。补录记录需显式标识“非平台来源”，并保留填报人、填报时间、数据依据及附件信息。  
补录数据进入统计后，应支持按合同、期间、项目经理等维度拆解展示；对无过程轨迹数据，页面需明确展示数据完整性状态与可追溯范围，避免与平台内全流程数据混淆。

### 2.9 差旅导入模板字段（员工编号、WBS）

**归属模块**  
O&M-差旅报销导入

**建议写入 SRS 文案**  
差旅报销导入模板需将“员工编号”“WBS”设为必填字段：员工编号用于定位员工主数据，WBS 用于映射合同编号并完成合同维度归集。模板说明应明确字段定义、取值规则、示例格式和常见错误。  
导入校验需覆盖格式合法性、主数据存在性、合同映射有效性、时间期间一致性及重复导入识别。校验失败时系统应生成可下载错误清单，逐条说明失败原因与修复建议。

### 2.10 回款自动冲抵规则（FIFO）

**归属模块**  
O&M-回款管理与核销

**建议写入 SRS 文案**  
回款核销采用统一 FIFO（先开先抵）规则，适用于“新增回款”和“导入回款”两类场景。系统需先筛选同合同下未冲抵开票记录，再按开票日期升序执行冲抵；同日记录按开票单号升序处理。  
当回款金额小于待冲抵总额时，支持部分冲抵并保留剩余应冲抵金额；当回款金额大于待冲抵总额时，超额部分按异常规则处理并提示。每次冲抵必须生成可追溯核销明细，至少包含冲抵顺序、冲抵金额、冲抵前后余额、执行时间、执行主体与关联单据。

### 2.11 大盘透视分层展示

**归属模块**  
O&M-大盘透视

**建议写入 SRS 文案**  
大盘透视需按“项目经理总览 -> 合同明细”两层结构展示：第一层展示各项目经理管理范围内的总体负责额度与核心经营指标；第二层在点击后下钻至合同维度，展示开票、回款、产值、成本、毛利等明细信息。  
两层视图的口径应明确区分并分别计算，避免同屏混算造成误读；同时应支持跨层追溯，确保管理层从总览异常可快速定位到具体合同与业务记录。

### 2.12 提醒接收对象配置

**归属模块**  
O&M-提醒设置

**建议写入 SRS 文案**  
提醒接收对象来源于 O&M 现有角色体系，配置人可在角色范围内选择具体接收人，实现按业务场景灵活分发。系统应支持配置版本管理，记录配置人、生效时间、失效时间、变更原因，并提供历史版本回滚能力。  
对于关键预警场景，可配置最小必达角色集合，避免因误配置导致无人接收。

### 2.13 投递渠道规则（无短信）

**归属模块**  
O&M-消息通知

**建议写入 SRS 文案**  
消息投递渠道明确为“站内消息 + 工作邮箱”，不纳入短信渠道。站内消息为强制开启且不可关闭，确保系统内告警必达；工作邮箱可按模板或业务场景配置启停。  
系统需记录每次投递的渠道状态与结果回执，便于后续核查消息是否送达。

### 2.14 联系方式来源规则

**归属模块**  
O&M-消息通知

**建议写入 SRS 文案**  
通知所使用的邮箱与手机号均来源于员工主数据，系统发送时应优先读取最新有效联系方式。若联系方式缺失、格式非法或状态失效，系统应进行发送拦截并生成异常告警。  
该异常需支持责任归属与修复跟踪，保证消息链路问题可定位、可修复、可闭环。

### 2.15 利润预警消息明细粒度

**归属模块**  
O&M-利润预警

**建议写入 SRS 文案**  
利润预警消息除合同级预警值外，需附带派单级风险明细，至少包含派单标识、责任人、产值、成本、偏差值、风险等级与风险说明。接收人在消息中即可查看关键明细，减少二次跳转成本。  
系统应支持按派单维度展开查看和排序，便于快速定位高风险项并推动责任人处理。

### 2.16 全局导出弹框规则

**归属模块**  
O&M-全局导出

**建议写入 SRS 文案**  
全局导出弹框应完整展示当前页面可导出字段，默认全选，支持按需勾选、全选、一键清空，并实时显示“可导出行数/已选字段数/是否含敏感字段”等信息。  
导出文件必须遵循页面当前展示口径（筛选条件、排序条件、字段集合），并记录导出任务日志（导出人、导出时间、导出范围、导出字段、任务结果），满足审计要求。

## 3. 门户系统

### 3.1 全平台消息统一分发

**归属模块**  
门户-消息汇聚与分发

**建议写入 SRS 文案**  
全平台消息能力采用“业务系统接入 -> 门户汇聚 -> 门户统一分发至 APP”的总体架构。O&M、PECMS 等系统统一按标准消息协议上送门户，门户负责标准化、路由分发、状态跟踪与失败重试。  
门户需提供统一消息模型、渠道策略、优先级规则、回执机制和补偿机制，确保跨系统消息在触达口径、展示样式、追踪能力上保持一致。

## 4. OA/泛微系统

### 4.1 对接前置条件与实施边界

**归属模块**  
OA/泛微-集成前置管理

**建议写入 SRS 文案**  
涉及 OA/泛微能力接入的需求（消息、出勤等）需设置实施前置条件：在开发联调前，由软件公司与泛微侧完成能力确认与边界澄清，明确可用接口、字段支持、调用频率、认证方式、回执机制、异常策略及职责分工。  
未完成前置确认的能力项不得进入联调与上线阶段。确认结果应形成书面接口基线，作为后续开发、测试、验收和运维的共同依据。
