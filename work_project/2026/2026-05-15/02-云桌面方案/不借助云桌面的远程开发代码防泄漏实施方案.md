# 不借助云桌面的远程开发代码防泄漏实施方案

## 一、文档目标

本文给出一套**不借助云桌面**、但尽量实现**代码不落本机、全过程可控、行为可审计、降低代码外泄风险**的落地方案。

目标不是做到“绝对无法泄漏”，而是做到：

1. 开发者电脑不直接保存业务源码。
2. Git 仓库、制品库、测试环境、发布环境仅允许通过受控入口访问。
3. 开发、调试、构建、发布全过程有统一入口、统一权限、统一审计。
4. 在甲方现有 `4` 台移动云服务器和本地测试机柜基础上，新增最少必要组件实现远程开发。

---

## 二、当前甲方资源映射

### 1. 已知现状

| 资源 | 当前情况 | 建议定位 |
| --- | --- | --- |
| `4` 台移动云服务器 | 已购买，分别部署不同系统 | 继续作为业务系统、测试系统、预发布系统或正式发布目标，不默认作为远程开发平台底座 |
| 本地机柜 | 含防火墙和华三路由，当前用于测试服务器 | 作为本地测试区、联调区、特殊网络访问区 |
| 开发者电脑 | 现场开发人员使用 | 仅作为接入终端，不保存源码，不直接连接 Git/服务器 |

### 2. 建议新增资源

| 资源 | POC 最小配置建议 | 正式环境建议 | 用途 |
| --- | --- | --- | --- |
| VPN / 零信任入口节点 | `1` 台 | `2` 台主备 | 开发者接入受控内网 |
| 远程开发控制节点 | `1` 台 | `2` 台主备或至少 `1` 台独立控制节点 | 承载 Coder 控制面 |
| 远程开发工作区计算节点 | `1-2` 台 | `2-4` 台 | 承载每个开发者的远程工作区 |
| GitLab 自建节点 | `1` 台 | `1-2` 台 | 代码仓库、包仓库、容器仓库、CI/CD |
| 堡垒机 / 审计节点 | `1` 台 | `1` 台 | 服务器访问审计、命令留痕、文件传输审计 |
| 日志汇聚节点 | 可与堡垒机同机（POC） | 独立节点 | 汇总 Git、VPN、堡垒机、工作区日志 |

说明：

- 若现有 `4` 台移动云服务器负载已经较高，不建议强行复用为远程开发平台底座。
- **正式环境**更推荐“新增远程开发资源”，现有 `4` 台服务器继续作为被访问、被调试、被发布的目标环境。

## 三、总体架构

### 1. 推荐目标架构

```text
开发者电脑
  -> WireGuard / 零信任入口
  -> Coder 统一门户
  -> 个人远程开发工作区
  -> GitLab 私有代码仓库 / 包仓库 / 容器仓库
  -> GitLab CI/CD
  -> JumpServer 堡垒机
  -> 现有4台移动云服务器
  -> 本地机柜测试服务器
  -> 审计 / DLP / 日志汇聚
```

### 2. 架构原则

1. **代码不落本机**  
   本机只安装接入客户端和 IDE 前端，不 `git clone` 业务源码。

2. **仓库不对本机开放**  
   Git、制品库、数据库、测试服务器只允许远程工作区网段、CI/CD 或堡垒机访问。

3. **服务器不允许本机直连**  
   业务服务器和测试服务器一律通过 JumpServer 或 CI/CD 访问。

4. **行为必须可回放、可追责**  
   Git 审计、堡垒机会话审计、文件传输审计、登录审计、CI 发布审计全部保留。

## 四、推荐软件组合

### 1. 核心组合

| 层级 | 推荐软件 | 作用 | 选型原因 |
| --- | --- | --- | --- |
| 接入层 | `WireGuard` | 开发者电脑接入受控内网 | 轻量、自建方便、POC 实施快 |
| 远程开发门户 | `Coder` | 统一创建、分配、管理远程开发工作区 | 自托管、运行在自有基础设施、支持 VS Code / JetBrains |
| IDE 客户端 | `VS Code Remote SSH` / `JetBrains Gateway` | 本机作为轻客户端接入远端工作区 | 保留开发习惯，不在本机存源码 |
| 代码与流水线 | `GitLab Self-Managed` | Git 仓库、包仓库、容器仓库、CI/CD | 一体化程度高，适合自建 |
| 服务器访问审计 | `JumpServer` | SSH/RDP/数据库访问审计、命令留痕、文件传输审计 | 适合统一纳管业务服务器和本地测试服务器 |
| 日志与审计汇聚 | `GitLab Audit + JumpServer Audit + Coder Audit` | 审计留痕 | 先用各组件原生日志，后续再汇总到 SIEM |

### 2. 增强组合

| 层级 | 推荐软件 | 作用 | 是否必选 |
| --- | --- | --- | --- |
| 设备合规 | `Microsoft Intune` | 受管终端、设备合规、公司电脑纳管 | 可选，推荐正式环境使用 |
| 条件访问 | `Microsoft Entra Conditional Access` | 只允许合规设备访问企业资源 | 可选，推荐正式环境使用 |
| 终端 DLP | `Microsoft Purview Endpoint DLP` | 阻断 USB、复制、打印、上传等敏感外发行为 | 可选，作为增强手段 |

说明：

- **核心组合**就可以实现“代码不落本机 + 统一入口 + 行为可审计”。
- **增强组合**主要用于“终端合规”和“浏览器/文件外发限制”，不是主链路，但有利于补强。

## 六、各阶段具体要做什么、用什么软件、怎么操作

## 阶段 0：边界确认与资源盘点

### 1. 要做的事

1. 盘点现有 `4` 台移动云服务器分别承载的系统。
2. 确认本地机柜测试服务器 IP、端口、网络段、访问方式。
3. 确认研发技术栈：
   `Java / Node.js / npm / Maven / Docker / 数据库工具 / APP调试需求`
4. 确认开发人数、并发人数、是否允许 BYOD。
5. 确认仓库选型是 GitLab 自建还是 GitHub 企业版。

### 2. 需要沟通的资源

| 对象 | 需要确认的信息 |
| --- | --- |
| 基础设施/网络 | 移动云 VPC、子网、安全组、NAT、出口 IP、机柜网段 |
| 安全部门 | 是否允许远程开发、是否要求终端合规、是否要求 DLP |
| 开发负责人 | IDE 类型、JDK/Node 版本、Maven/npm 源、数据库工具 |
| 运维负责人 | 发布流程、现有 CI、服务器 SSH/RDP 入口、域名/证书 |
| 账号管理员 | 是否已有 AD/LDAP/Entra ID |

### 3. 输出物

- `系统与服务器清单`
- `网络拓扑初稿`
- `账号与权限矩阵`
- `POC 范围说明`

## 阶段 1：网络接入打通

### 1. 目标

让开发者电脑只能先进入受控内网，再访问远程开发门户、工作区、Git、JumpServer。

### 2. 软件

- `WireGuard`

官方参考：  
https://www.wireguard.com/quickstart/

### 3. 实施步骤

#### 3.1 VPN 网关部署

1. 新建 `VPN-GW-01` 节点。
2. 安装 WireGuard。
3. 开放 UDP 监听端口，例如 `51820`。
4. 只放行开发所需网段，不做全量公网代理。

#### 3.2 生成服务端和客户端密钥

```bash
umask 077
wg genkey > server.key
wg pubkey < server.key > server.pub

wg genkey > client01.key
wg pubkey < client01.key > client01.pub
```

#### 3.3 配置服务端接口

示例 `/etc/wireguard/wg0.conf`：

```ini
[Interface]
Address = 10.10.10.1/24
ListenPort = 51820
PrivateKey = <server_private_key>

[Peer]
PublicKey = <client01_public_key>
AllowedIPs = 10.10.10.11/32
```

#### 3.4 启动接口

```bash
wg-quick up wg0
wg show
```

#### 3.5 路由策略

只允许客户端访问以下网段：

- Coder 门户网段
- 工作区网段
- GitLab 网段
- JumpServer 网段
- 本地机柜测试网段

不允许客户端通过 VPN 直接访问其它未授权服务器。

### 4. 实现效果

- 开发者电脑必须先连 VPN，才能看到开发资源。
- Git、服务器、测试环境不暴露给公网。

### 5. 本阶段验收

- 未连 VPN 无法访问 `Coder`、`GitLab`、`JumpServer`
- 连 VPN 后能访问受控资源
- VPN 仅打通必要子网

## 阶段 2：远程开发门户与工作区

### 1. 目标

开发者电脑只作为入口，不保存源码；每个开发者在远端独立工作区中开发。

### 2. 软件

- `Coder`
- `VS Code Remote SSH`
- `JetBrains Gateway`

官方参考：  
- https://coder.com/docs/about  
- https://code.visualstudio.com/docs/remote/ssh  
- https://www.jetbrains.com/help/idea/remote-development-overview.html

### 3. 实施步骤

#### 3.1 部署 Coder 控制面

1. 新建 `DEV-CTRL-01` 节点。
2. 配置域名，例如 `dev.company.local` 或 `dev.company.com`。
3. 安装 Docker / 容器运行环境。
4. 部署 Coder 控制面。
5. 配置 HTTPS 证书。

#### 3.2 接入统一身份认证

优先顺序建议：

1. 企业 `AD/LDAP/Entra ID`
2. 无企业目录时，POC 阶段可先用本地账号

目标要求：

- 每人唯一账号
- 禁止共享账号
- 权限按项目组划分

#### 3.3 创建开发工作区模板

每个模板建议预装：

- Ubuntu LTS
- JDK
- Maven
- Node.js
- pnpm / npm
- Git
- Docker / Podman
- 数据库客户端
- 浏览器
- 常用调试工具

建议至少做两个模板：

1. `Java + Vue/Web` 模板
2. `接口/脚本/运维辅助` 模板

#### 3.4 设置工作区策略

在 Coder 中配置：

1. 每人一个独立工作区
2. 自动休眠 / 自动关机
3. CPU / 内存 / 磁盘配额
4. 工作区默认无公网直出，按需经代理访问

#### 3.5 开发者接入方式

**方式 A：VS Code**

1. 本机安装 VS Code
2. 安装 `Remote - SSH`
3. 通过 Coder 或 SSH 连接远端工作区
4. 打开远程目录，开始开发

**方式 B：JetBrains**

1. 本机安装 JetBrains Gateway
2. 创建到远端工作区的连接
3. 启动远端 IDE backend
4. 在本机 JetBrains Client 中开发

### 4. 实现效果

- 源码、依赖、构建产物都在远端工作区
- 本机只是显示和输入
- 本机丢失或更换，不会遗留完整源码

### 5. 本阶段验收

- 开发者可以正常打开远程工程
- 能在远端编译、运行、调试
- 本机不出现完整业务源码目录

## 阶段 3：Git 仓库、包仓库、容器仓库、CI/CD

### 1. 目标

代码、依赖、镜像、流水线统一纳管，不允许本机直连仓库。

### 2. 软件

- `GitLab Self-Managed`

官方参考：  
- Package Registry: https://docs.gitlab.com/user/packages/package_registry/  
- Container Registry: https://docs.gitlab.com/user/packages/container_registry/  
- IP restrictions: https://docs.gitlab.com/administration/reporting/ip_addr_restrictions/  
- Audit events: https://docs.gitlab.com/user/compliance/audit_event_types/

### 3. 实施步骤

#### 3.1 部署 GitLab

1. 新建 `DEV-GIT-01` 节点。
2. 部署 GitLab Self-Managed。
3. 使用私有域名，例如 `git.company.local`。
4. 仅开放给 VPN 网段、工作区网段、CI 节点访问。

#### 3.2 项目结构设计

建议：

- 按项目建 `Group`
- 按系统或模块建 `Project`
- 仓库统一设为 `Private`

#### 3.3 启用私有包仓库

GitLab Package Registry 可承载：

- `Maven`
- `npm`
- `Generic packages`

典型做法：

1. 在项目中启用 Packages 功能
2. 使用 CI 发布 Maven / npm 包
3. 只允许工作区和 CI 拉取

示例 `.npmrc`：

```ini
@company:registry=https://git.company.local/api/v4/projects/<project_id>/packages/npm/
```

Maven `settings.xml` 示例：

```xml
<mirrors>
  <mirror>
    <id>company-maven</id>
    <url>https://git.company.local/api/v4/groups/<group_id>/-/packages/maven</url>
    <mirrorOf>*</mirrorOf>
  </mirror>
</mirrors>
```

#### 3.4 启用容器仓库

1. 在 GitLab 管理端启用 Container Registry
2. 为每个项目提供镜像命名空间
3. CI/CD 统一构建并推送镜像

登录示例：

```bash
docker login git.company.local:5050
```

#### 3.5 配置 CI/CD

建议：

1. GitLab Runner 放在受控网段
2. Runner 只接受受控项目任务
3. 正式发布必须走 CI/CD，不允许人工从本机上传包

#### 3.6 权限与审计

1. 强制一人一号
2. 关键分支保护
3. 关键环境仅允许 Maintainer / Release 角色发布
4. 打开审计事件和日志导出

### 4. 实现效果

- 代码仓库仅受控访问
- Maven/npm/镜像依赖统一从私有仓库获取
- 构建、打包、发布有流水线记录

### 5. 本阶段验收

- 开发者本机不能直接访问 GitLab
- 工作区可以正常克隆、提交、推送
- CI 能构建并发布包/镜像

## 阶段 4：服务器访问与本地机柜纳管

### 1. 目标

现有 `4` 台移动云服务器和本地机柜测试服务器统一纳入访问审计，不允许开发者本机直连。

### 2. 软件

- `JumpServer`

官方参考：  
- 产品说明：https://docs.jumpserver.org/  
- 快速入门：https://docs.jumpserver.org/zh/master/admin-guide/quick_start/  
- 会话命令审计：https://docs.jumpserver.org/zh/v4/en/manual/admin/audit/session_audit/session_command/  
- 文件传输审计：https://docs.jumpserver.org/zh/v4/manual/admin/audit/session_audit/file_transfer/

### 3. 实施步骤

#### 3.1 部署 JumpServer

1. 新建 `DEV-JUMP-01` 节点。
2. 配置域名，例如 `jump.company.local`。
3. 配置基础系统参数、站点 URL、邮件。

#### 3.2 录入资产

按资产类型录入：

- 现有 `4` 台移动云服务器
- 本地机柜测试服务器
- 若需要，可录入数据库资产

每台资产配置：

- IP
- 端口
- 系统类型（Linux / Windows / DB）
- 管理账号

#### 3.3 创建用户、用户组、资产权限

1. 按项目组建立用户组
2. 按环境建立资产组
3. 只授权需要访问的项目成员
4. 禁止共享超级管理员口令

#### 3.4 强制访问路径

要求：

- 开发者只能从工作区访问 JumpServer
- JumpServer 再访问目标服务器
- 目标服务器安全组只允许 JumpServer 和必要的 CI/CD IP

#### 3.5 开启审计

重点打开：

1. 会话录像
2. 命令审计
3. 文件传输审计
4. 作业日志
5. 平台操作日志

### 4. 本地机柜接入步骤

1. 在移动云侧建立到本地机柜的 `IPSec VPN / 专线 / 逻辑专网`
2. 在机柜防火墙上放通：
   - 工作区到测试服务器的访问
   - JumpServer 到测试服务器的访问
3. 在华三路由上配置对应静态路由
4. 做连通性验证

### 5. 实现效果

- 所有服务器登录都经 JumpServer
- 谁访问了哪台服务器、执行了什么命令、传了什么文件都能查

### 6. 本阶段验收

- 本机直连服务器被阻断
- 工作区可通过 JumpServer 登录服务器
- 命令审计和文件传输审计可查询

## 阶段 5：终端合规与 DLP 增强

### 1. 目标

如果开发者使用公司电脑，进一步限制复制、打印、USB、上传等高风险行为。

### 2. 软件

- `Microsoft Intune`
- `Microsoft Entra Conditional Access`
- `Microsoft Purview Endpoint DLP`

官方参考：  
- Intune + Conditional Access: https://learn.microsoft.com/en-us/intune/device-security/conditional-access-integration/overview  
- Intune Compliance: https://learn.microsoft.com/en-us/intune/device-security/compliance/overview  
- Purview Endpoint DLP: https://learn.microsoft.com/en-us/purview/endpoint-dlp-learn-about?view=o365-worldwide  
- Edge for Business DLP: https://learn.microsoft.com/en-us/deployedge/microsoft-edge-security-dlp

### 3. 实施步骤

#### 3.1 设备纳管

1. 把公司电脑纳入 Intune
2. 建立合规策略：
   - 必须磁盘加密
   - 必须有杀毒
   - 必须设置锁屏密码
   - 必须保持在线上报

#### 3.2 条件访问

1. 在 Entra / Conditional Access 中建立策略
2. 仅允许“合规设备”访问 `Coder`、`GitLab` 等企业应用
3. 不合规设备直接阻断

#### 3.3 DLP 策略

对高敏感目录、压缩包、导出物设置限制：

1. 阻断复制到 USB
2. 阻断打印
3. 阻断上传到非授权云盘
4. 阻断浏览器复制外发

注意：

- DLP 适合作为**补强**，不是主链路。
- 真正降低代码泄漏风险的关键仍是“代码不落本机”。

### 4. 实现效果

- 即使开发者用公司电脑访问远程开发入口，也能进一步限制常见外发方式。

### 5. 本阶段验收

- 不合规设备无法登录开发平台
- USB / 打印 / 外传策略生效
- DLP 事件可查

## 七、各软件的具体操作清单

## 1. WireGuard

### 要做什么

- 让开发者先进入受控网络，再访问开发资源

### 关键操作

1. 安装 WireGuard
2. 生成服务端、客户端密钥
3. 配置 `wg0.conf`
4. 启动 `wg-quick up wg0`
5. 配置路由，只允许开发相关网段
6. 把客户端配置下发给开发者

### 实现效果

- 开发者不在公司办公网，也能进入受控开发网络
- Git、Coder、JumpServer 不暴露公网

## 2. Coder

### 要做什么

- 提供统一远程开发门户和工作区生命周期管理

### 关键操作

1. 部署 Coder 控制面
2. 配置域名和 HTTPS
3. 接企业登录
4. 创建工作区模板
5. 设置资源配额和自动休眠
6. 给项目组分配模板访问权限

### 实现效果

- 每个开发者有独立工作区
- 工作区可秒级拉起、停用、重建
- 本机只作为 IDE 前端

## 3. VS Code Remote SSH / JetBrains Gateway

### 要做什么

- 让开发者继续使用熟悉的 IDE，但代码和运行环境在远端

### 关键操作

**VS Code**

1. 安装 VS Code
2. 安装 `Remote - SSH`
3. 配置远端工作区 SSH 连接
4. 打开远程项目目录
5. 在远端工作区中构建、调试

**JetBrains**

1. 安装 JetBrains Gateway
2. 配置远程工作区地址
3. 启动远端 IDE backend
4. 用本地 JetBrains Client 开发

### 实现效果

- 维持本地 IDE 体验
- 不需要在本机保存项目源码

## 4. GitLab Self-Managed

### 要做什么

- 统一提供 Git、包仓库、镜像仓库、CI/CD

### 关键操作

1. 部署 GitLab
2. 创建 Group / Project
3. 仓库统一设为 `Private`
4. 打开 Package Registry 和 Container Registry
5. 配置 Runner
6. 打开审计事件
7. 工作区访问仓库，本机禁止直连

### 实现效果

- 代码、依赖、镜像、流水线统一平台管理
- 发布链路可追踪

## 5. JumpServer

### 要做什么

- 统一纳管服务器访问，记录命令、录像、文件传输

### 关键操作

1. 部署 JumpServer
2. 配置站点地址、邮件、管理员
3. 录入移动云服务器和本地机柜测试服务器
4. 建立用户组、资产组、授权规则
5. 开启会话录像、命令审计、文件传输审计
6. 目标服务器安全组只允许 JumpServer 访问

### 实现效果

- 本机不能直接 SSH/RDP
- 所有敏感访问都有录像和命令留痕

## 6. Intune + Conditional Access + Purview DLP

### 要做什么

- 对公司电脑做合规纳管和敏感操作限制

### 关键操作

1. 把公司电脑加入 Intune
2. 建设备合规策略
3. 在 Conditional Access 中要求合规设备访问企业资源
4. Onboard 设备到 Endpoint DLP
5. 建立 DLP 规则：阻断 USB、打印、上传、复制

### 实现效果

- 只有合规设备能访问开发平台
- 常见外发路径有阻断和审计

## 九、最终建议

如果甲方的真实目标是“尽量避免代码外泄”，且不想采用传统云桌面，那么最合理的路线不是“允许源码下载到本机再装监控软件”，而是：

`开发者电脑 -> WireGuard/零信任 -> Coder 远程开发工作区 -> GitLab 私有代码仓库/包仓库/CI -> JumpServer 访问服务器 -> 现有4台移动云服务器和本地机柜测试环境`

其中：

- **核心控制点**：代码不落本机
- **核心准入点**：开发者必须先进入受控网络，再进入远程开发门户
- **核心审计点**：Git、工作区、堡垒机、CI/CD 全部留痕
- **核心边界**：现有 `4` 台移动云服务器优先作为业务目标，不默认充当远程开发底座
