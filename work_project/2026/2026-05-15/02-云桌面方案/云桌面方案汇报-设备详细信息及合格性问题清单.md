| 4 | 适配性风险已被供应商主动暴露 | 供应商明确要求评估云服务器与云终端软件适配性 | 当前兼容性不是已验证事项，而是待验证事项 |
| 5 | 单机风险仍然存在 | 当前正式清单只有 `1` 台桌面云服务器 | 一旦宿主机故障，`10` 名开发人员将整体中断 |
| 6 | 承载能力缺少实证 | 虽然 `CPU` 已升级为双路 `8370C`，但供应商仍未提供 `10` 人并发研发的压测或验证结果 | 不能直接向领导说明“已经验证可稳定支撑” |
| 7 | 配套环境边界不清 | 代码仓库、数据库、缓存、测试环境、日志平台等没有明确是甲方现有、供应商新建，还是二期建设 | “代码与环境全部留在我司”的目标仍缺落地边界 |
| 8 | 现有资源与云桌面整合路径不清 | 甲方已有 `4` 台移动云服务器和 `1` 个本地测试机柜，但文档未明确各自的归属和角色 | 难以判断哪些沿用、哪些新建、哪些应纳入本次交付边界 |
| 9 | 强制“只能经云桌面开发”的控制闭环未写清 | 未明确代码仓库、测试服务器、部署服务器是否只对白名单云桌面网段/堡垒机开放 | 本地电脑仍可能绕过云桌面直接访问环境，代码隔离目标难以真正落地 |
| 10 | PPT 能力与报价清单不一致 | 图中出现了 `安全网关`、`外网桌面池`、`iTrans`、`网盘`、`黑白名单`、`录屏/水印/防截屏` 等能力，但清单并未逐项报价 | 汇报时若直接引用 PPT 能力，容易被追问“哪些已买、哪些未买、哪些仅是能力说明” |
| 11 | 安全控制不完整 | 文件出口控制补了，但屏幕侧泄露风险没有在正式供货边界中闭环 | 仍不能宣称“绝对无法带走代码或资料” |
| 12 | 权限审计依赖外部系统 | `AD/LDAP`、`HR`、后端日志系统、备份系统都依赖企业现有平台或额外集成 | 若甲方没有现成系统，当前方案不能直接落地 |
| 13 | 报价清单存在疑点 | 服务器配置中仍写“`2块960TB SSD作为虚机系统盘`” | 说明 `V2` 报价清单本身仍需供应商勘误和二次确认 |

## 三、总结建议

`供应商最新 V2 报价清单较上一版在硬件算力和能力描述上确有增强，但供应商最新又进一步明确提出：云服务器和终端需处于同一局域网、云服务器与终端软件适配性需要评估、若采用移动云服务器则必须先做 POC。结合这一新增口径，当前方案已不宜再表述为“可继续推进的一期基础方案”，更准确的状态应表述为“待 POC 验证的候选方案”：即方案方向可以继续研究，但在 10 人真实研发承载、移动云兼容性、网络前提、现有 4 台移动云服务器的角色归位、PPT 能力与实际供货边界一致性、屏幕侧防泄露、审计闭环和备份体系闭环前，不能直接认定为正式定版方案。`

## 四、自带电脑前提下的必要与非必要项总结

以下判断以前提为准：`开发人员使用自带笔记本电脑直接接入云桌面`。

### 1. 必要项

| 序号 | 项目 | 当前判断 | 说明 |
| --- | --- | --- | --- |
| 1 | 桌面云计算服务器 | 必要 | 这是承载云桌面虚拟机的核心资源，没有服务器就无法落云桌面 |
| 2 | 桌面云管理平台及 `10` 个 `VDI` 授权 | 必要 | 没有管理平台和授权，无法统一分配、管理和控制 `10` 个研发桌面 |
| 3 | 安全策略配置能力 | 必要 | 本地盘映射、文件传输、`USB`、剪贴板、打印、网络出口控制是代码隔离的核心能力 |
| 4 | 权限与审计能力 | 必要 | 一人一账号、按项目授权、日志留痕是驻场研发场景的必要控制条件 |
| 5 | 网络接入能力 | 条件必要 | 如果现场没有可复用网络接入资源，接入交换机有必要；如果现场工位已有足够网络口和现成交换资源，则不一定必须单独采购 |

### 2. 非必要项

| 序号 | 项目 | 当前判断 | 说明 |
| --- | --- | --- | --- |
| 1 | 办公云终端 `10` 个 | 非必要 | 如果开发人员直接用自带笔记本接入云桌面，则云终端不再是必需采购项；它只在“统一终端接入、不允许个人电脑直接接入”时才有必要 |
| 2 | 显示器 `10` 台 | 非必要 | 如果开发人员使用自带笔记本且现场已有可复用显示设备，显示器不是代码隔离的必要采购项；仅在需要固定工位外接屏办公时才有保留价值 |

### 3. 可选保留项

| 序号 | 项目 | 当前判断 | 说明 |
| --- | --- | --- | --- |
| 1 | 云终端 + 显示器组合 | 可选 | 如果公司希望把驻场开发做成“统一工位、统一接入终端、不允许个人电脑直连云桌面”的管理模式，则这两项可以保留 |
| 2 | 接入交换机 | 可选 | 如果现有办公区交换资源不足，则建议保留；如果现网已满足，则可以不单独采购 |

结论口径：

`在“开发人员自带电脑直接接入云桌面”的前提下，报价清单中的云终端和显示器均不属于必要采购项；接入交换机是否保留，则取决于现场现有网络资源是否已经满足接入。`

## 五、按实际研发使用场景的承载判断

### 1. 假设使用场景

每名开发人员同时进行以下操作：

- 使用 `IDEA` 跑项目
- 使用 `Navicat` 等数据库可视化工具
- 使用 `Node.js` 环境下的 `uniapp` 等前端开发工具
- 打开 `WPS`
- 使用泛微 `e-mobile10` 聊天软件
- 使用 `SSH` 工具访问服务器
- 打开 `Google Chrome` 访问系统、报表工具等

### 2. 基于当前配置的判断

当前供应商给出的关键口径是：

- 宿主机：`2*8370C`，共双路 `64` 核级别 CPU
- 宿主机内存：`192GB`
- 单桌面：`4 vCPU / 12GB 内存 / 85GB SSD / 700GB HDD`
- 用户数：`10` 人

### 3. 承载分析

| 维度 | 当前情况 | 判断 |
| --- | --- | --- |
| `CPU` | 双路 `8370C` 相比旧版明显增强，`10` 个桌面按 `4 vCPU` 计算，共约 `40 vCPU` 口径 | `CPU` 层面比旧版有明显改善，基本具备支撑基础研发并发的条件 |
| 内存 | 每桌面仅 `12GB` | 对“`IDEA + 本地 Java 项目 + Node/uniapp + Chrome + Navicat + WPS + e-mobile10 + SSH` 同时打开”的场景来说，`12GB` 偏紧 |
| 磁盘与 I/O | 系统盘 `85GB SSD`，数据盘 `700GB HDD` | 如果项目代码、`Maven` 仓库、`npm`/`node_modules`、日志和临时文件主要落在 `HDD`，开发体验容易受影响 |
| 单机承载 | 仍是 `1` 台宿主机 | 即使日常能跑起来，一旦宿主机故障，`10` 人会整体中断 |

### 4. 是否够用

结论分两种情况：

| 使用强度 | 判断 | 说明 |
| --- | --- | --- |
| 轻中度使用 | 基本可用 | 如果更多是写代码、看日志、简单调试、偶尔启动服务，当前 `V2` 比旧版明显更有可用性 |
| 重度并发使用 | 不能直接认定为“稳定不卡顿” | 如果 `10` 个人都长期同时在 `IDEA` 本地启动项目、跑 `Node/uniapp`、开浏览器、开 `Navicat`、开 `WPS`、挂 `SSH` 和聊天工具，当前 `4 vCPU / 12GB` 口径不能直接保证流畅不卡顿 |

### 5. 主要瓶颈判断

当前最可能的瓶颈不是 `CPU`，而是：

1. `单桌面 12GB 内存偏紧`  
`IDEA + Java 进程 + Node/uniapp + Chrome + Navicat + WPS + e-mobile10 + SSH` 同开时，内存压力很容易上来，出现切换卡顿、索引变慢、编译等待、浏览器占用偏高等情况。

2. `研发数据若落在 HDD，I/O 体验会偏慢`  
Java 项目索引、`Maven` 依赖、`npm` 安装、`uniapp` 热更新、日志滚动和浏览器缓存都对磁盘响应比较敏感，如果关键研发目录主要落在 `HDD`，会出现“能用但不丝滑”的情况。

3. `单机架构不适合承诺高稳定性`  
即使日常性能能接受，也不能承诺“绝对不卡”或“完全无中断风险”。

### 6. 对当前场景的最终判断

建议汇报口径如下：

`按当前 V2 配置，若开发人员只是进行中等强度的 Java/前端开发、文档处理、数据库连接和日常系统访问，整体比上一版明显更有可用性；但如果 10 名开发人员长期同时在 IDEA 中本地启动项目，并同时运行 Navicat、Node/uniapp、WPS、e-mobile10、SSH、Chrome 等工具，则当前单桌面 4 vCPU / 12GB 的配置不能直接保证持续流畅不卡顿，尤其内存和磁盘 I/O 仍可能成为主要瓶颈。`

### 7. 如需更稳，建议补充的口径

如果要更有把握地支撑上述场景，建议至少补充确认：

- 单桌面是否可提升到 `16GB` 内存及以上
- 项目代码目录、`Maven` 仓库、`npm` 缓存、日志目录是否可落在 `SSD/NVMe`
- 是否做过 `10` 人并发 `IDEA + Node + Chrome + Navicat` 的压测或 `POC`
- 是否需要双屏办公
- 是否要保留云终端，还是直接采用“自带电脑接入”模式

## 六、结合甲方现有环境的访问与部署路径建议

### 1. 甲方现有资源归位建议

| 资源 | 当前情况 | 建议定位 |
| --- | --- | --- |
| `4` 台移动云服务器 | 甲方现有，已部署不同系统 | 作为甲方现有业务/部署资源池使用；需进一步划分哪些承载现有业务，哪些可承担代码仓库、制品库、测试环境或正式系统部署 |
| 本地机柜 | 机柜内已有防火墙和华三路由，当前用于测试服务器 | 作为本地测试区或联调区使用；建议只允许通过受控网络从云桌面访问，不建议开发人员个人电脑直接连接 |
| 云桌面平台 | 本次 `V2` 方案核心新增资源 | 作为研发人员统一开发入口、统一访问入口和统一审计入口，而不是简单新增一批办公终端 |

### 2. 如何控制“大家只能使用云桌面访问代码”

| 控制点 | 建议做法 | 目的 |
| --- | --- | --- |
| 用户接入入口 | 只允许开发人员从个人电脑或云终端访问云桌面网关，不允许个人电脑直接访问 `Git`、数据库、测试服务器、发布服务器的 `SSH/RDP/VPN` | 把个人电脑隔离在代码访问链路之外 |
| 代码仓库和环境白名单 | `Git`、制品库、数据库、测试服务器、发布服务器仅对白名单云桌面网段或堡垒机开放 | 确保代码和环境只能从云桌面侧访问 |
| 发布和运维方式 | 发布动作在云桌面内完成，或由云桌面触发受控 `CI/CD`、堡垒机、发布脚本完成 | 避免在本地电脑保留源码、制品和发布凭据 |
| 终端侧防外带策略 | 持续禁用本地磁盘映射、`USB`、剪贴板、打印、非授权外网通道；如需更严，可叠加水印、截屏/录屏管控 | 降低代码和资料外带风险 |
| 账号与审计 | `AD/LDAP + 一人一号 + MFA + Workspace/堡垒机审计`，服务器操作、`Git` 拉取、文件发布全部留痕 | 形成可追责、可审计的闭环 |

### 3. 云桌面访问与部署路径建议

| 场景 | 建议路径 | 说明 |
| --- | --- | --- |
| 开发人员访问代码和环境 | `个人电脑/云终端 -> 云桌面网关 -> 云桌面虚机 -> Git/依赖仓库/数据库` | 个人电脑只看到云桌面画面，不直接接触代码仓库和数据库 |
| 部署到甲方现有 `4` 台移动云服务器 | `云桌面 -> 堡垒机或发布工具 -> 4 台移动云服务器` | 云桌面可视为研发和运维跳板；建议后续把 `4` 台服务器按开发/测试/正式或按系统角色进一步拆清 |
| 部署到本地机柜测试服务器 | `云桌面 -> VPN/专线/受控网络策略 -> 本地机柜防火墙/华三路由 -> 测试服务器` | 本地机柜不是回到开发人员本地电脑，而是作为受控测试目标，通过机柜网络设备放通指定访问路径 |
| 统一自动化发布 | `开发人员在云桌面提交代码 -> CI/CD 在受控服务器拉取代码并发布到目标服务器` | 比人工拷贝发布更规范，也更容易统一审计 |

### 4. 对当前疑问的直接回答口径

- `“怎么控制大家都只能使用云桌面访问代码”`：关键不是口头要求，而是让 `Git`、数据库、测试服务器、发布服务器只对白名单云桌面网段或堡垒机开放，本地电脑没有直连权限。
- `“服务器部署系统的时候，怎么使用云桌面进行访问”`：把云桌面当作统一研发和运维入口，在云桌面里通过 `SSH/RDP/发布工具/堡垒机` 访问甲方现有 `4` 台移动云服务器。
- `“部署到本地机柜上的路径是什么”`：逻辑访问路径应是 `云桌面 -> 受控网络 -> 本地机柜 -> 测试服务器`；至于服务器上的实际部署目录，应按目标服务器操作系统和应用部署标准另行定义，不由云桌面本身决定。

### 5. 关于“服务器只对堡垒机开放，公网现场人员如何访问系统”的解释

这个问题的关键，在于必须区分两条完全不同的访问链路：

| 链路类型 | 访问对象 | 主要访问人群 | 建议开放内容 | 是否必须经过堡垒机 |
| --- | --- | --- | --- | --- |
| 管理链路 | 服务器管理面、发布面、数据库管理面、代码仓库管理面 | 开发人员、运维人员、实施人员 | `SSH`、`RDP`、数据库管理端口、发布端口、管理后台地址 | 是 |
| 业务访问链路 | 已部署完成的业务系统前台/业务入口 | 现场用户、甲方业务人员、外部访问人员 | `80/443` 或业务域名入口 | 否 |

因此，“服务器只对堡垒机开放”这句话，准确口径应为：

- `服务器的管理端口只对堡垒机或云桌面白名单开放`
- `业务系统的访问端口按业务需要对最终用户开放`

也就是说，受限的是“谁能管理服务器、谁能发布代码、谁能直连数据库”，而不是“谁能访问已经发布好的业务系统页面”。

### 6. 推荐访问拓扑说明

#### 6.1 公网现场人员访问正式业务系统的拓扑

```text
公网现场人员/甲方业务用户
        |
        v
互联网 / 运营商网络
        |
        v
域名解析 / 公网入口
        |
        v
WAF / 负载均衡 / 反向代理(Nginx)
        |
        v
应用服务器(移动云)
        |
        v
数据库/缓存/文件存储(内网)
```

说明：

- 现场人员访问的是 `业务域名` 或 `https://系统地址`。
- 现场人员通常只访问 `80/443` 对应的 Web 入口，不接触服务器管理端口。
- 更规范的做法是：公网只暴露 `WAF/负载均衡/反向代理`，后端应用服务器尽量放在内网，不直接暴露管理面。

#### 6.2 开发、发布、运维链路的拓扑

```text
开发人员个人电脑 / 云终端
        |
        v
云桌面网关
        |
        v
云桌面虚机
        |
        +------> Git / 制品库 / 依赖仓库
        |
        +------> 堡垒机
                    |
                    +------> 移动云应用服务器
                    |
                    +------> 数据库管理入口
                    |
                    +------> 本地机柜测试服务器
```

说明：

- 开发人员本地电脑不直接连接目标服务器。
- 代码拉取、编译、打包、数据库访问、远程登录、发布操作均在云桌面内完成。
- 堡垒机负责运维审计、命令留痕、账号控制和目标主机访问控制。

#### 6.3 本地机柜测试环境访问拓扑

```text
云桌面虚机
    |
    v
VPN / 专线 / 政企专网 / 受控互联策略
    |
    v
本地机柜防火墙
    |
    v
华三路由 / 交换网络
    |
    v
本地测试服务器
```

说明：

- 本地机柜测试服务器不应对开发人员个人电脑直接开放。
- 正确方式是先打通“云桌面侧到本地机柜侧”的受控网络，再通过机柜内防火墙和路由放行指定访问。
- 这样既能保留本地测试环境，又不破坏“只能经云桌面访问代码和环境”的控制目标。

### 7. 端口开放原则建议

| 对象 | 典型端口/入口 | 建议开放对象 | 说明 |
| --- | --- | --- | --- |
| 正式业务系统 Web 入口 | `80/443` | 公网用户或指定办公网用户 | 给现场人员、甲方业务人员访问系统页面 |
| 堡垒机入口 | `堡垒机地址 + MFA` | 开发、运维、实施白名单人员 | 用于管理和发布，不给普通业务人员使用 |
| Linux 服务器管理 | `22` | 仅堡垒机或云桌面白名单 | 禁止开发人员本地电脑直连 |
| Windows 服务器管理 | `3389` | 仅堡垒机或云桌面白名单 | 禁止公网直接暴露 |
| 数据库管理 | `3306/5432/1433` 等 | 应用服务器、堡垒机、云桌面白名单 | 不对公网开放 |
| Git/制品库 | `22/443/8081` 等 | 云桌面网段、CI/CD、堡垒机 | 确保代码仓库只在受控环境中使用 |
| 测试服务器 Web 入口 | 测试域名或内网地址 | 云桌面、测试人员白名单、VPN 用户 | 一般不建议直接对公网开放 |

### 8. 不同系统场景下的建议口径

| 场景 | 建议方式 | 原因 |
| --- | --- | --- |
| 正式对外业务系统 | 可通过公网域名提供访问，但管理端口仍仅对堡垒机开放 | 既满足现场访问，又不暴露管理面 |
| 内部办公系统 | 建议通过 `VPN`、零信任或办公专网访问 | 不一定需要完全公网开放 |
| 测试系统/联调系统 | 建议仅对云桌面、测试白名单或 `VPN` 用户开放 | 避免测试环境直接暴露公网 |
| 数据库、代码仓库、发布服务器 | 不对公网开放 | 这些属于研发和运维控制面，不属于业务访问面 |

### 9. 建议汇报结论口径

可直接用于汇报的解释如下：

`“服务器只对堡垒机开放”并不是指所有业务访问都必须先登录堡垒机，而是指服务器的管理端口、发布端口、数据库管理端口等只对堡垒机或云桌面白名单开放；现场人员通过互联网访问系统时，走的是业务访问链路，即‘互联网用户 -> 域名/WAF/反向代理 -> 业务系统’，访问的是系统页面入口而不是服务器管理入口。因此，‘代码和运维管理必须经过云桌面/堡垒机’与‘公网现场人员可正常访问已部署系统’这两件事是可以同时成立的。”`

## 七、基于供应商新增口径的再判断与 POC 前置建议

### 1. 新增口径带来的判断变化

| 新增口径 | 对判断的直接影响 |
| --- | --- |
| 云服务器和终端需要在同一个局域网下 | 当前方案不再能按“互联网任意接入 + 移动云天然可用”理解，必须先确认是否满足同局域网或同逻辑专网前提 |
| 需要评估云服务器和云终端软件适配性 | 说明移动云服务器、云终端、`Workspace`、控制器、安全网关等之间兼容性未被证明 |
| 如果采用移动云服务器需要做 `POC` | 说明移动云承载云桌面基础设施不是现成成熟交付，而是待验证路径 |
| 方案图存在多种模式 | 说明供应商尚未把本项目收敛为唯一落地架构，当前仍处于方案选型/验证阶段 |

### 2. 对当前项目更合理的两种落地理解

| 路径 | 说明 | 当前判断 |
| --- | --- | --- |
| 路径 A：本地或同逻辑内网部署 `H3C` 云桌面基础设施 | 将 `H3C UIS + Workspace + 终端/客户端` 视为单独建设的云桌面底座，甲方现有 `4` 台移动云服务器主要作为业务系统部署目标、测试目标或发布目标 | 可继续深化设计，但仍需明确网络、权限、安全和供货边界 |
| 路径 B：直接使用甲方现有 `4` 台移动云服务器承载 `H3C` 云桌面基础设施 | 把现有移动云服务器直接当作当前云桌面底座资源池 | 当前只能视为 `POC` 候选路径，未经验证不能直接下结论 |

### 3. 建议供应商必须补充确认的事项

| 序号 | 待确认事项 | 需要供应商明确的内容 |
| --- | --- | --- |
| 1 | “同一个局域网”定义 | 是必须物理同园区局域网，还是 `VPN/专线/政企专网` 形成的逻辑内网也可接受 |
| 2 | 本项目属于哪种模式 | 当前项目到底对应 `开发VDI + 上网PC`、`开发本地PC + 上网VDI` 还是 `开发/上网双VDI` |
| 3 | 移动云兼容范围 | 若使用移动云服务器，哪些版本、哪些网络模式、哪些客户端终端属于已验证兼容范围 |
| 4 | 方案图中的能力是否包含在本次报价 | `安全网关`、`外网桌面池`、`iTrans`、`网盘`、`黑白名单`、`安全审计`、`录屏`、`水印`、`防截屏` 是否已含在 `167300` 元报价内 |
| 5 | 终端形式 | 是必须采购瘦终端，还是普通电脑安装 `VDI` 客户端即可；若用普通电脑，终端兼容清单是什么 |
| 6 | 访问现有资源的方式 | 云桌面如何访问甲方现有 `4` 台移动云服务器和本地机柜测试服务器，哪些链路是已验证，哪些只是设计思路 |

### 4. 建议 POC 的最小验收项

| 序号 | 验证项 | 验证目标 |
| --- | --- | --- |
| 1 | 网络前提验证 | 验证“同一局域网”是否可通过 `VPN/专线/逻辑专网` 满足，而非必须物理同园区 |
| 2 | 终端兼容性验证 | 验证普通开发电脑或供应商云终端接入 `Workspace` 的实际可用性、稳定性和外设支持情况 |
| 3 | 移动云兼容性验证 | 验证若以移动云服务器承载云桌面基础设施，控制器、管理平台、桌面池、网络策略是否能正常工作 |
| 4 | 10 人真实研发负载验证 | 按 `IDEA + Node/uniapp + Navicat + WPS + SSH + Chrome` 等真实负载验证并发体验 |
| 5 | 访问现有 `4` 台移动云服务器验证 | 验证云桌面是否能稳定访问现有业务服务器，并完成代码拉取、调试、发布等动作 |
| 6 | 访问本地机柜测试环境验证 | 验证云桌面到机柜防火墙/华三路由后的测试服务器访问是否稳定、是否满足测试发布需求 |
| 7 | 安全策略验证 | 验证 `USB`、剪贴板、文件传输、打印、本地盘映射、上网隔离、水印/录屏/防截屏等能力的实际生效情况 |
| 8 | 审计留痕验证 | 验证用户登录、桌面连接、文件传输、`Git` 操作、服务器访问、发布操作是否有完整审计链路 |
| 9 | 故障恢复验证 | 验证断线重连、桌面快照、异常恢复和简单回滚能力 |
| 10 | 汇报口径验证 | 最终形成“哪些能力已验证通过、哪些仅为设计能力、哪些不在本次供货范围”的清单，避免 PPT 能力被误当成交付事实 |

### 5. 建议新增汇报结论口径

可直接用于汇报的口径如下：

`结合供应商最新口径，本项目当前不能再直接按“移动云服务器上现成部署一套云桌面即可落地”理解。供应商已经明确提出，同一局域网前提、云服务器与终端软件适配性以及移动云路径下的 POC 验证，均属于前置条件。这说明当前方案方向可以继续推进，但状态应定义为“待 POC 验证的候选方案”，而不是“可直接定版实施的正式方案”。若甲方希望继续沿移动云路径推进，必须先完成兼容性和真实场景 POC；若改为本地或同逻辑内网单独部署 H3C 云桌面底座，则现有 4 台移动云服务器更适合作为业务系统部署目标，而不是直接等同于当前云桌面的宿主资源池。`
